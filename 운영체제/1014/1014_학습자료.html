ATM 앞에 통장 10개 든 사람, 먼저 보내 주는 게 이득일까?

SJF(최단 작업 우선) ★ · 비선점형 · 평균 대기 시간 20ms · 기아 현상 ★ · 에이징 ★

통장 하나만 정리하면 되는데, 앞사람 손에 통장이 10개

"저 하나만 먼저 하면 안 될까요?" 이 생각을 알고리즘으로 만든 게 SJF예요. 교재 비유로는 정수기 앞에서 큰 물통 여러 개 채우는 사람이 물 한 잔 마실 사람에게 양보하는 것.

SJF(Shortest Job First, 최단 작업 우선)는 준비 큐에 있는 프로세스 중 실행 시간이 가장 짧은 작업부터 CPU를 주는 비선점형 알고리즘이에요. 도착 순서는 상관없어요.

10/12와 같은 데이터(P1 도착 0 · 30ms, P2 도착 3 · 18ms, P3 도착 6 · 9ms)로 풀어 볼게요. P1은 혼자 먼저 와서 바로 시작하고, 비선점이라 끝까지 가요. P1이 끝난 30에서 보니 P2(18)와 P3(9)가 있으니 짧은 P3가 먼저예요.

프로세스도착실행시작 ~ 끝대기 시간 (시작 − 도착)
P10300 ~ 300
P36930 ~ 3930 − 6 = 24
P231839 ~ 5739 − 3 = 36
평균(0 + 24 + 36) ÷ 3 = 20ms (FCFS 23ms보다 짧음)

그런데 왜 실제로는 못 쓸까 — 두 가지

  • 종료 시간 예측의 어려움 — 프로세스가 언제 끝날지 미리 알기 어려워요. 문서 편집기처럼 사용자 입력을 기다리는 프로그램은 몇 분에 끝날지 몇 시간에 끝날지 몰라요. 악의적인 프로세스가 작업 시간을 속일 수도 있고요.
  • 공평성 위배 — 짧은 작업이 계속 들어오면 긴 작업은 계속 뒤로 밀려요. "나는 비켜 주기로 했는데, 저쪽에서 통장 하나 든 사람이 10명이 와 버리면?"

이렇게 특정 프로세스가 CPU나 자원을 계속 할당받지 못하는 상태가 기아 현상(starvation, 아사 현상)이에요. "굶어 죽는" 거죠. 완화하는 방법은 에이징(aging) — 양보할 때마다 나이를 한 살씩 먹게 해서, 예를 들어 세 살(세 번 양보)이 되면 더는 양보하지 않고 무조건 먼저 실행해요. 다만 그 기준을 몇 살로 할지(3번? 5번? 100번?) 정해야 하는 문제가 남아요.

시험엔 이렇게

SJF는 준비 큐의 프로세스 중 실행 시간이 가장 짧은 작업부터 CPU를 할당하는 비선점형 알고리즘으로, 콘보이 효과를 해결해 평균 대기 시간이 짧다. 그러나 종료 시간 예측이 어렵고, 긴 작업이 계속 뒤로 밀리는 기아 현상이 생겨 공평성에 위배된다. 기아 현상은 특정 프로세스가 CPU나 자원을 계속 할당받지 못하는 상태이며, 양보할 때마다 나이를 먹게 해 상한선을 정하는 에이징으로 완화할 수 있다.

외우는 법: 짧은 놈 먼저 → 긴 놈은 굶는다(기아) → 나이 먹이기(에이징)
바로 확인
P1(도착 0, 6ms) · P2(도착 1, 3ms) · P3(도착 2, 8ms) · P4(도착 3, 2ms)를 SJF로 처리하면 실행 순서는?
0에 P1만 있으니 P1이 먼저, 비선점이라 6까지 끝까지. 그다음 남은 것 중 짧은 순: P4(2) → P2(3) → P3(8). 대기 시간은 0 + 3 + 7 + 9 = 19, 평균 4.75.

오래 기다린 사람에게 점수를 더 주면, 굶는 사람이 줄어들까?

HRN(최고 응답 우선) ★ · 비선점형 · 응답률 = (대기 + CPU 사용) ÷ CPU 사용 ★

HRN(Highest Response Ratio Next, 최고 응답 우선)은 SJF에서 생길 수 있는 기아 현상을 완화하는 비선점형 알고리즘이에요. SJF는 CPU 사용 시간만 봤다면, HRN은 대기 시간과 실행 시간을 모두 고려해서 우선순위를 정해요. 그 기준이 응답률이에요.

응답률 공식 (교재 밑줄)
응답률 = (대기 시간 + CPU 사용 시간) ÷ CPU 사용 시간
응답률이 높을수록 우선순위가 높다는 점에 주의! 오래 기다릴수록(분자↑), 작업이 짧을수록(분모↓) 숫자가 커져요.

같은 데이터로 계산해 볼게요. P1은 혼자라 먼저 실행(0~30). 30 시점에서 P2와 P3 중 고르려면 응답률을 계산해요.

30 시점대기 시간CPU 사용 시간응답률
P2 (도착 3)30 − 3 = 2718(27 + 18) ÷ 18 = 2.5
P3 (도착 6)30 − 6 = 249(24 + 9) ÷ 9 ≈ 3.67 → 먼저 실행

그래서 P3(30~39) → P2(39~57). 평균 대기 시간은 (0 + 24 + 36) ÷ 3 = 20ms로 SJF와 같아요. 공평성을 조금 더 챙기지만 여전히 실행 시간이 긴 프로세스가 불리하고, SJF처럼 실행 시간을 미리 알아야 해서 실제로 널리 쓰이지는 않아요. 교수님이 그래도 가르친 이유는 "응답률 공식이 정보처리기사 시험에 가끔 나와서"예요.

시험엔 이렇게

HRN은 SJF에서 발생할 수 있는 기아 현상을 완화하는 비선점형 알고리즘으로, 대기 시간과 실행 시간을 모두 고려해 우선순위를 결정한다. 응답률 = (대기 시간 + CPU 사용 시간) ÷ CPU 사용 시간이며, 응답률이 높을수록 높은 우선순위를 가진다.

외우는 법: (기다린 것 + 할 것) ÷ 할 것, 큰 놈이 먼저
바로 확인
대기 시간 20, CPU 사용 시간 5인 프로세스 A와, 대기 시간 30, CPU 사용 시간 15인 프로세스 B. HRN에서 먼저 실행되는 것은?
A = (20 + 5) ÷ 5 = 5, B = (30 + 15) ÷ 15 = 3. 응답률이 높은 A가 먼저예요. 단순히 오래 기다린 순서가 아니에요.

회전목마처럼 10ms씩 돌아가며 — 평균 대기 시간은 정말 줄었을까?

라운드 로빈(RR) ★ · 선점형 · 현대 스케줄링의 기본 ★ · 대기 시간 합 67 · 문맥 교환 ★

여기까지(FCFS · SJF · HRN)는 비선점형이라 지금은 거의 안 써요. 이제부터가 선점형이고, 그 대표 주자가 라운드 로빈(RR, Round Robin)이에요. 교수님 비유로 회전목마(merry-go-round)처럼 돌아가요.

모든 프로세스가 일정한 시간(타임 슬라이스) 동안만 CPU를 쓰고, 작업이 안 끝나면 준비 큐의 맨 뒤로 가서 다시 차례를 기다려요. FCFS와 비슷하지만 타임 슬라이스를 적용한다는 점이 다르고(FCFS의 선점형 버전), 한 프로세스가 CPU를 독점하지 못해 긴 작업을 무작정 기다리는 콘보이 효과가 줄어요. 교재: "선점형 알고리즘 중 가장 단순하고 대표적인 방식", "시분할 시스템의 기본 스케줄링 방식".

타임 슬라이스 10ms로 계산 (그림 5-20)

  1. P1은 도착하자마자 10ms 실행 후 큐 맨 뒤로. 대기 0
  2. P2는 3에 도착해 10에 시작. 대기 7
  3. P3는 6에 도착해 20에 시작, 9ms 만에 종료. 대기 14
  4. P1은 10에 멈췄다가 29에 재시작. 대기 19
  5. P2는 20에 멈췄다가 39에 재시작, 남은 8ms 실행 후 종료. 대기 19
  6. P1은 39에 멈췄다가 47에 재시작, 남은 10ms 실행 후 종료. 대기 8
  7. 총 대기 시간 0 + 7 + 14 + 19 + 19 + 8 = 67ms, 평균 67 ÷ 3 ≈ 22.33ms

핵심 요령: 다시 시작할 때의 대기 시간은 "이번 시작 시각 − 지난번에 멈춘 시각"이에요. 처음 시작할 때만 "시작 − 도착".

교수
시간 계산하는 거 시험 문제 낼 수도 있어요. 나누기 3을 하면 계산하기 힘드니까, 평균 대기 시간 대신 총 대기 시간의 합으로 내 버리면 되잖아요. 그럼 67을 답으로 써야 되는 거야. 저 생각보다 머리 좋습니다.10/14 강의 중 (말을 조금 다듬음)

22.33 < 23, 그래서 FCFS보다 빠를까? — 문맥 교환 (교재 별표)

숫자는 FCFS(23ms)보다 아주 조금 작아요. 그런데 교재에 별표가 있는 문장: 선점형인 RR 스케줄링에는 문맥 교환 시간이 추가되기 때문에 평균 대기 시간을 절대적인 성능 지표로 볼 수 없어요. FCFS는 한 번 잡으면 끝까지 가지만 RR은 계속 번갈아 바뀌니까, 바뀔 때마다 문맥 교환 시간이 들고, 오히려 더 느려질 수도 있어요.

또 타임 슬라이스 설정이 중요해요. 너무 길면 FCFS처럼 동작해 한 프로세스가 독점하고, 너무 짧으면 문맥 교환이 빈번해 오버헤드가 커져요(9/28 내용). 그래서 현대 운영체제는 기본적으로 RR을 활용하고, 여기에 우선순위를 적용해 변형한 형태를 써요.

시험엔 이렇게

라운드 로빈(RR)은 모든 프로세스가 일정한 시간(타임 슬라이스) 동안만 CPU를 사용하고, 작업이 끝나지 않으면 준비 큐의 맨 뒤로 이동해 다시 차례를 기다리는 선점형 알고리즘으로, 선점형 중 가장 단순하고 대표적인 방식이자 시분할 시스템의 기본 스케줄링 방식이다. 우선순위를 고려하지 않으며, 문맥 교환 시간이 추가되므로 평균 대기 시간만으로 성능을 판단할 수 없다.

외우는 법: RR = 회전목마, 10ms 타고 줄 맨 뒤로 · 재시작 대기 = 이번 시작 − 지난번 멈춤
바로 확인
위 RR 예제에서 P1이 두 번째로 CPU를 받을 때(29)의 대기 시간은?
P1은 10에 멈췄으니 29 − 10 = 19. 처음 도착 시각(0)으로 빼는 건 첫 시작 때만이에요.

성능은 무지막지하게 좋은데 쓸 수 없는 알고리즘, 그리고 "중요도"

SRT(최소 잔여 시간) ★ · SJF의 선점형 · 평균 15.66ms · 우선순위 스케줄링 · 표 5-4

SRT(Shortest Remaining Time, 최소 잔여 시간)는 SJF를 선점형으로 바꾼 것이에요. 라운드 로빈과 SJF의 특징을 결합해서, 남아 있는 작업 시간이 더 적은 프로세스에 먼저 CPU를 줘요. 교재 그림처럼 타임 슬라이스(10ms)가 끝나면 남은 시간이 가장 적은 프로세스가 선택돼요.

순서무슨 일대기 시간
0 ~ 10P1 먼저 10ms 실행 → 남은 20, 큐로P1 0
10 ~ 19남은 시간이 가장 적은 P3(9) 실행 후 종료P3 10 − 6 = 4
19 ~ 37다음으로 적은 P2(18) 실행 후 종료P2 19 − 3 = 16
37 ~ 57P1 남은 20 실행 후 종료P1 37 − 10 = 27
총 · 평균0 + 4 + 16 + 27 = 47, 47 ÷ 3 ≈ 15.66ms

SJF(20ms)보다도 훨씬 짧아요. 제일 긴 P1이 10만 하고 맨 뒤로 쫓겨나니까요. 그런데도 못 써요. SJF와 마찬가지로 종료 시간을 예측하기 어렵고 기아 현상이 생기고, 남은 실행 시간을 주기적으로 계산해야 해서 오버헤드도 커요. 교수님 말로 "성능은 무지막지하게 좋으나 쓸 수가 없다".

우선순위를 고려한 스케줄링 — 우선순위의 진짜 이유는 "중요도"

프로세스의 중요도에 따라 우선순위(priority)를 주고, 더 높은 프로세스를 먼저 실행할 수 있어요. 우선순위는 비선점형에도 선점형에도 적용할 수 있어요.

유형스케줄링우선순위 부여 기준 (교재 표 5-4)
비선점형최단 작업 우선(SJF)작업 시간이 짧은 프로세스에 높은 우선순위
비선점형최고 응답 우선(HRN)작업 시간이 짧거나 대기 시간이 긴 프로세스에 높은 우선순위
선점형최소 잔여 시간(SRT)남은 작업 시간이 짧은 프로세스에 높은 우선순위

즉 "남은 시간"을 우선순위로 쓰면 SJF · SRT가 돼요. 하지만 교수님 강조: 우선순위를 쓰는 근본 이유는 남은 시간이 아니라 중요도예요. 커널 프로세스가 일반 프로세스보다 중요하니까 우선순위를 주는 거죠. 교재: 우선순위 스케줄링은 시스템 효율성보다 각 프로세스의 중요도에 따라 우선순위를 부여하는 방식이고, 대부분의 현대 운영체제가 이 방식을 채택해요. 단점도 있어요. 낮은 우선순위의 프로세스가 오래 실행되지 못하는 기아 현상, 우선순위를 계속 정렬해야 하는 오버헤드, 사용자 프로세스와 커널 프로세스의 우선순위가 같게 설정되면 생기는 안정성 문제.

시험엔 이렇게

SRT는 SJF 스케줄링을 선점형으로 변환한 것으로, 라운드 로빈과 SJF의 특징을 결합해 남아 있는 작업 시간이 더 적은 프로세스에 먼저 CPU를 할당한다. 평균 대기 시간은 짧지만 종료 시간 예측이 어렵고 기아 현상이 발생하며 오버헤드가 커 실제로는 널리 쓰이지 않는다. 우선순위 스케줄링은 각 프로세스의 중요도에 따라 우선순위를 부여하는 방식으로 비선점형과 선점형 모두에 적용할 수 있다.

외우는 법: SJF + 선점 = SRT · 우선순위의 근본 = 중요도

장면 5

라운드 로빈 + 우선순위 = MLQ. 그런데 맨 아래 큐는 왜 영영 차례가 안 올까?

다단계 큐(MLQ) ★ = RR + priority · 고정 우선순위 · 다단계 피드백 큐(MLFQ) ★ · 변동 우선순위 · 맨 아래는 FCFS ★ · 리눅스

교수님의 결론: 지금 컴퓨터에서 꼭 쓰는 건 라운드 로빈과 우선순위 두 가지. 이 둘을 합친 게 다단계 큐(MLQ, Multi-Level Queue)예요(필기: MLQ = RR + priority).

MLQ는 우선순위에 따라 여러 개의 준비 큐를 사용하는 고정 우선순위 방식이에요. 프로세스는 자기 우선순위에 맞는 큐에 들어가고, 각 프로세스는 독립적으로 스케줄링되며, 우선순위가 높은 큐가 먼저 실행돼요. 각 큐 안은 라운드 로빈으로 돌아가요. 커널 프로세스를 높은 큐에, 사용자 프로세스를 낮은 큐에 둬서 커널이 늘 먼저 실행되게 할 수 있어요. 또 우선순위에 따라 타임 슬라이스 크기를 조절할 수도 있어요(사용자와 상호작용이 없는 후면 프로세스는 타임 슬라이스를 크게).

문제는 우선순위가 낮은 하위 큐의 프로세스는 실행이 계속 지연된다는 것. 보통 우선순위가 20~50개쯤인데, 위쪽 큐에 계속 새 프로세스가 들어왔다 나갔다 하면 맨 아래 큐는 실행될 확률이 거의 없어요(기아).

MLFQ — CPU를 쓸 때마다 우선순위를 낮춘다

이걸 개선한 게 다단계 피드백 큐(MLFQ, Multi-Level Feedback Queue)예요. 구조는 MLQ와 비슷하지만 프로세스의 우선순위가 동적으로 변하는 변동 우선순위 방식이에요.

  • CPU를 한 번 쓰고 나면 우선순위가 한 단계 낮아져요. 우선순위 큐에서 나가 CPU를 쓰고, 돌아올 때는 한 단계 아래 큐의 뒤로 들어가요. 그래서 CPU를 많이 쓴 프로세스는 점점 아래로 내려가고, 위쪽 큐가 계속 막히지 않아요.
  • 아래 큐일수록 타임 슬라이스가 커져요(교재 그림 5-24: 20 → 40 → 80 → …). 낮은 우선순위의 프로세스는 CPU를 잡기 어려우니까, 어렵게 잡았을 때 오래 쓰게 해 주는 거예요.
  • 맨 아래 큐는 타임 슬라이스가 무한대 = FCFS(선입선출) (교재 별표). 한 번 잡으면 끝까지 써요.

장점: 사용자 입력 대기 같은 대화형(단기) 작업은 빠르게 반응하고, 계산 위주의 배치(장기) 작업은 점점 낮은 큐로 내려가 CPU를 오래 쓰게 돼요. 단점: 각 우선순위의 타임 슬라이스 크기 설정이 어렵고, 악의적인 프로세스가 우선순위를 조작할 가능성이 있어요. 그래도 다양한 프로세스를 효과적으로 관리할 수 있어서 유닉스와 리눅스 같은 현대 운영체제에서 가장 널리 쓰여요.

코어가 둘인데 한쪽은 스레드 10개, 한쪽은 2개 — 나눠 줘야 할까?

멀티프로세서 스케줄링 · CPU 선호도(프로세스 선호도) ★ · 단일 큐(SQMS) · 다중 큐(MQMS) ★ · 부하 불균형 · 작업 훔치기 ★

지금까지는 CPU(코어) 하나에 누구를 올릴지였다면, 이제는 코어가 여러 개일 때 스레드를 어느 코어에 배분할지의 문제예요. 교수님이 대학 때 배운 교과서에는 스레드도, 이 내용도 없었대요. 멀티코어 CPU가 나중에 나왔으니까요.

P1에 스레드 10개, P2에 스레드 2개, 코어 1 · 2가 있다고 해 볼게요. P1을 코어 1에, P2를 코어 2에 몰아주면 코어 2는 금방 끝나고 놀아요. 그래서 6개씩 나눠 주면 양쪽이 비슷하게 바빠지죠(로드 밸런싱). 그런데 문제가 있어요.

CPU 선호도 — 같은 프로세스는 같은 코어에서 (교재 별표)

멀티코어 CPU에서 각 코어는 자기만의 캐시(cache)와 레지스터를 써서 데이터 접근 속도를 높여요. 코어 1에서 P1의 스레드 A가 돌면 코어 1의 캐시에는 P1의 데이터가 저장돼요. 그런데 P1의 스레드 B가 코어 2에서 돌면, 코어 2의 캐시를 비우고 P1의 데이터를 다시 가져와야 해서 성능이 떨어져요. 그래서 동일한 프로세스에 속한 스레드를 계속 같은 코어에서 실행시키는 것이 효율적이고, 이걸 CPU 선호도(affinity)라고 해요. 프로세스 선호도, 코어 선호도, 캐시 선호도라고도 해요. 윈도우에서는 작업 관리자에서 특정 프로세스가 몇 번 코어에서만 돌게 직접 지정할 수도 있어요.

결국 멀티코어에서 고민할 건 두 가지예요. 로드 밸런싱(양쪽 작업을 공평하게)과 CPU 선호도 유지. 이 둘이 서로 부딪혀요.

단일 큐 멀티프로세서 스케줄링 (SQMS)다중 큐 멀티프로세서 스케줄링 (MQMS)
방법모든 스레드를 하나의 큐에 넣어 스케줄링. 큐의 스레드를 비어 있는 코어에 하나씩 할당코어마다 별도의 큐를 배치. 각 코어는 하나 이상의 큐를 가지고 코어별로 독립적으로 스케줄링
장점스레드가 자동으로 균등 배분 → 로드 밸런싱이 수월, 기존 알고리즘을 그대로 쓸 수 있어 구현이 쉬움같은 프로세스의 스레드를 같은 큐에 넣어 CPU 선호도를 쉽게 구현, 캐시 활용도가 높음
단점CPU(프로세스) 선호도를 구현하기 어려움 (스레드 A · B가 다른 코어에서 실행되면 캐시 데이터 공유가 어려워 성능 저하)부하 불균형(load imbalance): 특정 큐에 스레드가 몰려 과부하인데 다른 큐는 비어 코어가 쉼
예웹 서버, 클라우드 서버 (모든 요청을 한 큐로 처리)윈도우 · 리눅스 · 맥OS 같은 일반적인 멀티코어 운영체제

작업 훔치기 — 놀고 있는 코어가 옆 큐에서 가져오기

부하 불균형 해결을 위해 스레드가 많은 큐에서 작업을 가져와 스레드가 없는 큐에 분배하는 기법을 작업 훔치기(work stealing)라고 해요. 그런데 작업 훔치기로 부하 불균형을 해결하면 CPU 선호도가 깨져요(교재 말풍선). 그래서 쉬운 일이 아니에요. 교수님 덧붙임: 실제로는 프로세스가 100개 넘게 돌고 코어는 많아야 수십 개라, 노는 코어가 생기기는 쉽지 않아요. 이론적인 이야기지만 "시험 문제 내는 사람 입장에서는 이런 문제가 제일 만만하다"고.

시험엔 이렇게

CPU 선호도(프로세스 선호도, 코어 선호도, 캐시 선호도)는 동일한 프로세스에 속한 스레드를 계속 같은 코어에서 실행시키는 것으로, 캐시를 비우지 않고 계속 활용해 성능이 향상된다. 단일 큐 멀티프로세서 스케줄링(SQMS)은 모든 스레드를 하나의 큐에 넣어 로드 밸런싱이 수월하지만 CPU 선호도를 구현하기 어렵고, 다중 큐 멀티프로세서 스케줄링(MQMS)은 코어마다 별도의 큐를 두어 CPU 선호도를 쉽게 구현하지만 부하 불균형이 생긴다. 부하 불균형은 작업 훔치기로 해결할 수 있으나 CPU 선호도를 해치게 된다.

외우는 법: 단일 큐 = 균형 ○ 선호도 ✗ / 다중 큐 = 선호도 ○ 균형 ✗ → 훔치기
바로 확인
코어마다 큐를 따로 두었더니 코어 1의 큐에만 스레드가 몰리고 코어 2는 쉬고 있다. 이 문제와 해결 기법은?
다중 큐 방식의 부하 불균형이에요. 코어 2가 코어 1의 큐에서 작업을 가져오는 작업 훔치기로 해결하지만 CPU 선호도는 깨져요.

① 비선점형 — FCFS · SJF · HRN FCFS 23 → SJF 20 = HRN 20

  • FCFS : 준비 큐에 도착한 순서대로 CPU를 주는 비선점형. 평균 대기 23ms, 약점은 콘보이 효과 (10/12)
  • SJF : 실행 시간이 가장 짧은 작업부터 CPU를 주는 비선점형. 평균 대기 20ms
  • 기아 현상 : 특정 프로세스가 CPU나 자원을 계속 할당받지 못하는 상태 (starvation)
  • 에이징 : 양보할 때마다 나이를 먹여 상한선을 정해 기아를 완화하는 기법
  • HRN : 대기 시간과 실행 시간을 모두 고려해 기아를 완화하는 비선점형
  • 응답률 : (대기 시간 + CPU 사용 시간) ÷ CPU 사용 시간. 높을수록 먼저

② 선점형 — RR · SRT ★ 계산

  • 라운드 로빈 : 타임 슬라이스 동안만 실행하고 안 끝나면 큐 맨 뒤로. 선점형의 대표 · 현대 스케줄링의 기본
  • RR 예제 : 대기 0 · 7 · 14 · 19 · 19 · 8 → 합 67, 평균 22.33. 재시작 대기 = 이번 시작 − 지난번 멈춤
  • RR 주의 : 문맥 교환 시간이 추가되므로 평균 대기 시간만으로 성능을 판단할 수 없다
  • SRT : SJF를 선점형으로 바꾼 것. 남은 시간이 적은 것부터. 평균 15.66이지만 기아 · 오버헤드로 안 씀

③ 우선순위 · 다단계 MLQ = RR + priority

  • 우선순위 스케줄링 : 프로세스의 중요도에 따라 우선순위를 부여. 비선점 · 선점 모두 가능
  • MLQ : 우선순위별 여러 큐, 고정 우선순위, 높은 큐 먼저, 각 큐는 RR. 하위 큐가 계속 지연
  • MLFQ : 변동 우선순위. CPU를 쓰면 우선순위가 낮아지고, 아래 큐일수록 타임 슬라이스가 커지며, 맨 아래는 FCFS. 리눅스 · 유닉스

④ 멀티프로세서 ★

  • CPU 선호도 : 같은 프로세스의 스레드를 계속 같은 코어에서 실행 (프로세스 · 코어 · 캐시 선호도)
  • SQMS : 단일 큐. 로드 밸런싱 수월, 선호도 구현 어려움
  • MQMS : 코어마다 큐. 선호도 쉬움, 부하 불균형 발생
  • 작업 훔치기 : 스레드가 많은 큐에서 빈 큐로 작업을 가져오는 기법. 선호도를 해침

빈칸 채우기 눌러서 정답 확인

실행 시간이 가장 짧은 작업부터 CPU를 주는 비선점형 알고리즘은 SJF이며, 긴 작업이 계속 밀리는 기아 현상이 생기고 이는 에이징으로 완화한다. HRN의 응답률은 (대기 시간 + CPU 사용 시간) ÷ CPU 사용 시간이며 응답률이 높을수록 먼저 실행된다. 타임 슬라이스만큼 실행 후 큐 맨 뒤로 가는 선점형 알고리즘은 라운드 로빈이고, SJF를 선점형으로 바꾼 것은 SRT다. 우선순위별 큐를 쓰는 고정 우선순위 방식은 MLQ, 우선순위가 동적으로 변하는 방식은 MLFQ이며 그 맨 아래 큐는 FCFS로 동작한다. 같은 프로세스의 스레드를 같은 코어에서 실행하는 것을 CPU 선호도라 하고, 다중 큐의 부하 불균형은 작업 훔치기로 해결한다.

키보드: Space 뒤집기 · → 알아요 · ← 모르겠어요
SJF란?
준비 큐의 프로세스 중 실행 시간이 가장 짧은 작업부터 CPU를 할당하는 비선점형 알고리즘.
SJF가 실제로 안 쓰이는 이유 2가지는?
종료 시간 예측의 어려움, 공평성 위배(긴 작업이 계속 밀리는 기아 현상).
기아 현상과 에이징이란?
기아 현상 = 특정 프로세스가 CPU나 자원을 계속 할당받지 못하는 상태. 에이징 = 양보할 때마다 나이를 먹게 해 양보 상한선을 정하는 완화 기법.
HRN 응답률 공식은?
(대기 시간 + CPU 사용 시간) ÷ CPU 사용 시간. 응답률이 높을수록 우선순위가 높다.
교재 예제에서 30 시점 P2, P3의 응답률은?
P2 = (27 + 18) ÷ 18 = 2.5, P3 = (24 + 9) ÷ 9 ≈ 3.67 → P3 먼저.
라운드 로빈이란?
모든 프로세스가 타임 슬라이스 동안만 CPU를 쓰고, 안 끝나면 준비 큐 맨 뒤로 가는 선점형 알고리즘. 현대 CPU 스케줄링의 기본.
RR 예제(10ms)의 총 대기 시간과 평균은?
0 + 7 + 14 + 19 + 19 + 8 = 67ms, 평균 ≈ 22.33ms.
RR의 평균 대기 시간이 FCFS보다 작은데도 더 빠르다고 할 수 없는 이유는?
선점형이라 문맥 교환 시간이 추가되기 때문.
SRT란? 평균 대기 시간은?
SJF를 선점형으로 바꾼 것으로 남은 작업 시간이 적은 프로세스부터 실행. 교재 예제 47 ÷ 3 ≈ 15.66ms.
우선순위를 쓰는 근본 이유는?
프로세스의 중요도(예: 커널 프로세스가 일반 프로세스보다 중요).
MLQ와 MLFQ의 차이는?
MLQ = 고정 우선순위, 하위 큐가 계속 지연. MLFQ = 변동 우선순위, CPU를 쓰면 우선순위가 낮아지고 아래 큐일수록 타임 슬라이스가 커짐(맨 아래 FCFS).
CPU 선호도란?
동일한 프로세스에 속한 스레드를 계속 같은 코어에서 실행시키는 것. 캐시를 계속 활용해 성능 향상.
SQMS와 MQMS의 장단점은?
SQMS(단일 큐) = 로드 밸런싱 수월 / 선호도 구현 어려움. MQMS(다중 큐) = 선호도 쉬움 / 부하 불균형.
작업 훔치기란?
부하 불균형 해결을 위해 스레드가 많은 큐에서 작업을 가져와 빈 큐에 분배하는 기법. CPU 선호도를 해친다.

    퀴즈 다 풀고 채점하기 · 계산 포함

    Q1교재 예제(P1 0/30, P2 3/18, P3 6/9)를 RR(타임 슬라이스 10ms)로 처리할 때 총 대기 시간은?

    0 + 7 + 14 + 19 + 19 + 8 = 67. 60은 SJF·HRN, 69는 FCFS, 47은 SRT의 합이에요.

    Q2같은 예제의 평균 대기 시간을 작은 순으로 바르게 나열한 것은?

    15.66 < 20 < 22.33 < 23. 다만 RR · SRT에는 문맥 교환 시간이 빠져 있어 이 숫자만으로 성능을 판단할 수는 없어요.

    Q3대기 시간 12, CPU 사용 시간 4인 프로세스의 HRN 응답률은?

    (12 + 4) ÷ 4 = 4.

    Q4다음 중 비선점형 알고리즘끼리 묶은 것은?

    비선점형 = FCFS · SJF · HRN, 선점형 = RR · SRT · MLQ · MLFQ (교재 표 5-2).

    Q5MLFQ에 대한 설명으로 틀린 것은?

    고정 우선순위 · 하위 큐 지연은 MLQ의 특징(문제점)이에요. MLFQ는 변동 우선순위로 이걸 고쳤어요.

    Q6단일 큐 멀티프로세서 스케줄링(SQMS)의 단점은?

    단일 큐는 균형이 잘 맞지만 같은 프로세스의 스레드가 다른 코어로 흩어져 캐시를 공유하기 어려워요. 부하 불균형은 다중 큐의 단점.

    Q7SJF에서 긴 작업이 계속 뒤로 밀리는 문제를 완화하려고, 양보 횟수에 상한선을 두는 기법은?

    양보할 때마다 나이를 먹게 해 몇 살이 되면 더 양보하지 않는 것 = 에이징. 기아 현상을 완화해요.

    Q8P1(도착 0, 6) · P2(1, 3) · P3(2, 8) · P4(3, 2)를 SJF로 처리할 때 평균 대기 시간은?

    P1 0~6(대기 0) → P4 6~8(6 − 3 = 3) → P2 8~11(8 − 1 = 7) → P3 11~19(11 − 2 = 9). (0 + 3 + 7 + 9) ÷ 4 = 4.75.

    내 말로 설명하기 친구한테 말하듯이

    FCFS → SJF → HRN → RR → MLQ → MLFQ로 오면서 각각 앞의 무엇을 고쳤는지 "기차 이론"처럼 이어서 설명해 보세요.

    FCFS는 도착 순서대로 끝까지 실행해서, 긴 작업 뒤의 짧은 작업이 오래 기다리는 콘보이 효과가 생겨요. 그래서 짧은 작업부터 하는 SJF가 나왔는데, 이번엔 긴 작업이 계속 밀리는 기아 현상이 생겨요. HRN은 대기 시간을 응답률에 넣어 오래 기다린 작업도 올라오게 해서 기아를 완화했지만, 여전히 실행 시간을 미리 알아야 하는 비선점형이라 안 써요. 선점형으로 넘어와서 RR은 타임 슬라이스만큼 돌아가며 써서 CPU 독점을 막았고, 지금 스케줄링의 기본이에요. 여기에 중요도에 따른 우선순위를 합친 게 MLQ인데 우선순위가 고정이라 아래 큐는 계속 지연돼요. 그래서 MLFQ는 CPU를 쓸 때마다 우선순위를 낮추고 아래 큐일수록 타임 슬라이스를 크게 줘서(맨 아래는 FCFS) 이 문제를 고쳤고, 리눅스가 이 방식을 써요.
