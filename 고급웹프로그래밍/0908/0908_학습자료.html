브라우저는 그냥 "인터넷 보는 프로그램" 아니야?

브라우저의 3역할 · 아키텍처 · JS 엔진 · 역사

브라우저는 우리가 짠 HTML · CSS · JS가 실제로 실행되는 플랫폼이에요. 서버에서 리소스를 받아 오고, HTML 구조를 해석해 CSS를 입혀 화면을 그리고, JS를 실행해 움직이게 해요. 자료의 한 줄 정의가 이거예요.

자료의 정의

Web Browser = Web Resource Fetcher + Rendering Engine + JS Runtime

외우는 법: 가져오고 · 그리고 · 실행하고
구성 요소하는 일

장면 2

컴퓨터는 "naver.com"을 모른다. 그럼 어떻게 찾아갈까?

DNS · 조회 순서 · 프로토콜 · 전체 흐름

사람은 www.naver.com 같은 이름을 쓰지만, 실제 네트워크 통신은 IP 주소로 해요. 그래서 서버에 연결하기 전에 이름을 IP로 바꾸는 단계가 필요해요. 이게 DNS(Domain Name System)예요. 교수님이 "이 변환 과정은 꼭 기억하라"고 했어요.

  1. 브라우저 DNS 캐시 — 전에 가 본 곳이면 여기서 바로
  2. OS DNS 캐시 — 없으면 운영체제에
  3. DNS 리졸버에 질의 → DNS 서버가 IP 반환
  4. 받은 IP로 웹 서버와 연결 시작

(실제 IP는 서버 구성 · 위치 · CDN에 따라 여러 개거나 바뀔 수 있어요.)

프로토콜 — 통신의 약속

프로토콜은 장치끼리 통신하려고 정한 규칙이에요(데이터 형식 · 전송 방법 · 순서 · 오류 처리). 같은 프로토콜만 쓰면 서로 다른 시스템도 대화할 수 있죠. 웹 페이지 하나 불러오는 데도 여러 프로토콜이 층층이 같이 쓰여요.

Protocol역할대표 용도
HTTP웹 리소스 요청 / 응답Web, REST API
HTTPS암호화된 HTTP대부분의 현대 웹
DNSDomain → IP 변환서버 위치 탐색
TCP신뢰성 있는 전송HTTP/1.1, HTTP/2
UDP빠른 비연결형 전송Streaming, DNS
TLS암호화 · 인증HTTPS
WebSocket양방향 실시간Chat, Game, 알림

그래서 전체 흐름은: URL 입력 → DNS 조회 → TCP/TLS 연결 → HTTP 요청 → 서버가 HTML · CSS · JS 반환 → 파싱 · JS 실행 → Render Tree → Layout → Paint → Composite → 화면.

시험엔 이렇게

DNS는 도메인 이름을 IP 주소로 변환하는 시스템으로, 브라우저는 서버 연결 전에 Browser DNS Cache → OS DNS Cache → DNS Resolver 순으로 조회한다. URL 입력 후 DNS Lookup → TCP/TLS 연결 → HTTP 요청 → 리소스 반환 → 렌더링 순으로 진행된다.

외우는 법: DNS 순서 브 · 오 · 리 / 전체 찾고 · 잇고 · 묻고 · 받고 · 그린다
바로 확인
어제 접속했던 사이트를 다시 열 때, IP를 얻으려고 가장 먼저 확인하는 곳은?
브 · 오 · 리. 캐시에 있으면 DNS 서버까지 안 가요.

장면 3

브라우저와 서버는 어떤 모양의 편지를 주고받을까?

HTTP Request 4요소 · Response 3요소 · 메시지 해석

HTTP는 Client–Server 기반 Request / Response 프로토콜이에요. 브라우저가 먼저 요청을 보내고, 서버가 처리해서 응답을 돌려줘요.

Request — "무엇을 해 달라"GET /products/10 HTTP/1.1      // Method + URL/Path
Host: example.com                 // ↓ Header: 추가 정보
Accept: application/json          // "응답은 JSON으로 주세요"
User-Agent: Chrome                // 요청한 브라우저
                                  // Body: GET은 보통 없음

Response — 처리 결과HTTP/1.1 200 OK                   // Status Code
Content-Type: application/json    // Header
Content-Length: 42
{ "id": 10, "name": "Keyboard" }  // Body: 실제 데이터
Request (4)Response (3)
Method 작업 종류 · URL/Path 리소스 위치 · Header 추가 정보 · Body 보낼 데이터Status Code 결과 숫자 · Header · Body (HTML · JSON · Image · File)

GET은 보통 Body를 안 쓰고, POST · PUT · PATCH는 Body를 써요. 그리고 상태 코드는 응답에만 있어요. 요청 메시지엔 상태 코드가 없어요.

직접 보려면: 크롬 F12 → Network 탭 → 네이버로 이동. 한 페이지를 띄우는 데 엄청나게 많은 요청이 일어나는 걸 볼 수 있어요.

시험엔 이렇게

HTTP Request는 Method · URL(Path) · Header · Body로, Response는 Status Code · Header · Body로 구성된다. GET 요청은 일반적으로 Body를 사용하지 않는다.

외우는 법: 요청 M · U · H · B / 응답 S · H · B
바로 확인
위 Request 메시지의 해석으로 옳은 것은?
GET + /products/10 = 조회, Accept = 원하는 응답 형식. 요청엔 상태 코드가 없어요.

로그인은 왜 POST고, 게시판 10페이지는 왜 GET일까? (면접 단골)

GET vs POST · 장단점 · 상황에 맞는 메서드

교수님 시연: 허깅페이스 모델 목록 주소 /models?p=1&sort=trending

p=1을 10으로 바꾸니 10페이지로 바로 이동. 2500으로 바꾸니 400 Bad Request.

주소 물음표 뒤 key=value가 보이면 GET이에요. 데이터를 URL에 실어 보내요. 그래서 주소만 바꿔서 원하는 페이지로 바로 가고, 링크로 공유하고, 테스트하기 쉬워요. 대신 데이터가 다 보여요.

POST는 데이터를 Body에 담아 보내요. 주소창에 안 보이니까 로그인 ID/PW, 글 작성처럼 노출되면 안 되는 요청에 써요. 대신 주소로 직접 접근 · 테스트하기 어려워요.

GETPOST
데이터 위치URL ?p=10&sort=trendingBody
장점주소로 바로 접근 · 공유 · 테스트 쉬움주소창에 노출 안 됨
단점데이터 노출 → 수정 작업엔 부적합직접 접근 · 테스트 어려움
예조회, 게시판 페이지, 상품 상세로그인, 글 작성 · 생성 · 수정
틀린 생각POST는 안 보이니까 보안이 되고, 그러니 무조건 POST
맞는 생각암호화는 메서드가 아니라 HTTPS(TLS)의 역할. HTTP면 POST Body도 평문. 정답은 "상황에 맞는 메서드"
시험엔 이렇게

GET은 데이터를 URL(?key=value)에 담아 리소스를 조회하며 공유 · 테스트가 쉽지만 데이터가 노출된다. POST는 Body에 담아 전송해 노출되지 않아 로그인 · 생성에 적합하지만 직접 접근이 어렵다. 상황에 맞는 메서드를 선택해야 한다.

외우는 법: GET은 주소에 · POST는 몸(Body)에 / 보이면 공유 쉽고, 안 보이면 노출 적다
바로 확인
다음 중 POST가 더 알맞은 것은?
개인정보를 서버에 보내서 생성하는 일 = POST. 나머지는 조회라 GET.

404는 내 잘못, 502는 서버 잘못?

상태 코드 2xx · 3xx · 4xx · 5xx

상태 코드는 첫 자리만 보면 돼요. 프론트엔드는 이걸 보고 성공 화면과 실패 화면을 나눠 보여 줘요.

범위의미대표 코드
2xx요청 성공200 OK · 201 Created
3xxRedirect (다른 곳으로 넘겨줌 — 실패 아님)301 · 302
4xxClient Error (내 요청 · 주소가 잘못)400 Bad Request · 401 · 403 · 404 Not Found
5xxServer Error (서버 쪽 문제)500 · 502 Bad Gateway · 503

교수님이 한신대 홈페이지 Network 탭을 열어 보니 bx-loader.gif가 404였어요. HTML이 요청한 경로에 그 파일이 없는 거죠. 그리고 502 Bad Gateway는 서버에서 잘못된 응답이 왔을 때 나는 에러로, 앞으로 많이 보게 될 거라고 했어요. 네이버 뉴스 링크를 누르면 신문사 페이지로 넘어가는 건 3xx(리다이렉트 성공).

시험엔 이렇게

상태 코드 2xx는 성공(200, 201), 3xx는 Redirect(301, 302), 4xx는 Client Error(400, 401, 403, 404), 5xx는 Server Error(500, 502, 503)이다.

외우는 법: 둘셋은 OK · 넷은 내 탓 · 다섯은 서버 탓
바로 확인
주소에 ?p=2500처럼 범위 밖 값을 넣어 요청했더니 받은 응답은? (강의 시연)
잘못된 요청 → 4xx. 시연 결과는 400.

카페 와이파이에서 로그인하면 비밀번호가 보일까? 그리고 서버는 왜 나를 기억 못 할까?

HTTP vs HTTPS (면접 단골 2번) · Stateless

HTTP는 기본적으로 암호화가 안 돼요. 로그인 ID/PW가 평문(Plain Text)으로 네트워크를 지나가니, 중간에서 가로채면 그대로 보여요(감청 · 탈취 · 위조 위험).

HTTPS(HTTP Secure)는 HTTP + TLS예요. 브라우저와 서버 사이 데이터를 암호화하고, 서버 인증서로 "진짜 그 서버가 맞는지" 신뢰성을 검증해요. 현대 웹에선 HTTPS가 기본이고, HTTP 사이트엔 크롬이 경고를 띄워요. 인증서는 복호화 키가 새면 안 되니 서버가 발급받아 설치 · 보관해요(TLS 자세한 건 9/10).

HTTPGET /login · ID/PW: Plain Text
HTTPSGET /login · ID/PW: Encrypted data

HTTP는 기억상실 — Stateless

HTTP의 각 요청은 서로 독립적으로 처리돼요. 서버는 기본적으로 이전 요청을 기억하지 않아요. 그래서 GET /login으로 로그인한 다음 GET /mypage를 요청해도, 서버는 HTTP만으로는 두 요청이 같은 사람인지 몰라요.

  • 장점 — 구조가 단순해서 서버 확장성과 처리 효율이 높아요.
  • 단점 — 로그인 여부, 사용자 ID, 장바구니, 권한 같은 상태는 따로 유지해야 해요 → 쿠키 · 세션 · 토큰 (9/10)
시험엔 이렇게

HTTP는 전송 데이터가 암호화되지 않는다. HTTPS는 HTTP에 TLS를 결합해 데이터를 암호화하고 서버 인증서로 서버의 신뢰성을 검증한다. HTTP는 Stateless라 각 Request를 독립적으로 처리하며, 상태 유지가 필요하면 Cookie · Session · Token을 사용한다.

외우는 법: S는 Secure · 열쇠(인증서)는 서버에 / HTTP는 기억상실
바로 확인
GET /login 후 GET /mypage를 보냈다. HTTP만으로 서버가 알 수 없는 것은?
HTTP는 Stateless. 같은 사람인지 알려면 쿠키 · 세션 · 토큰이 필요해요.

브라우저는 서버에 연결하기 전에 DNS 조회로 도메인 이름을 IP 주소로 바꾼다. HTTPS는 HTTP에 TLS를 결합한 것이다. GET은 데이터를 URL에, POST는 Body에 싣는다. 상태 코드 4xx는 클라이언트 오류, 5xx는 서버 오류다. 각 요청을 독립적으로 처리하는 HTTP의 특성을 Stateless라 한다.

키보드: Space 뒤집기 · → 알아요 · ← 모르겠어요
웹 브라우저의 한 줄 정의는?
Web Resource Fetcher + Rendering Engine + JS Runtime. 리소스를 요청 · 해석 · 실행 · 렌더링하는 플랫폼.
브라우저 4대 구성 요소는?
User Interface · Browser Engine(전체 제어) · Rendering Engine(DOM/CSSOM → 화면) · JavaScript Engine.
Chrome/Edge와 Safari의 JS 엔진은?
Chrome/Edge = V8, Safari = JavaScriptCore.
DNS 조회 순서는?
Browser DNS Cache → OS DNS Cache → DNS Resolver 질의 → IP 반환 → 서버 연결.
URL 입력부터 화면까지 순서는?
DNS Lookup → TCP/TLS 연결 → HTTP 요청 → 리소스 반환 → 파싱 · JS 실행 → Render Tree → Layout → Paint → Composite.
프로토콜이란?
장치 간 통신 규칙(데이터 형식 · 전송 방법 · 순서 · 오류 처리). 웹은 HTTP · DNS · TCP · TLS 등이 계층적으로 결합.
HTTP Request 4요소와 Response 3요소는?
Request = Method · URL/Path · Header · Body. Response = Status Code · Header · Body.
GET과 POST의 차이는?
GET: URL ?key=value, 공유 · 테스트 쉬움, 노출. POST: Body, 비노출, 직접 접근 어려움. 상황에 맞게 선택.
상태 코드 2 · 3 · 4 · 5xx는?
2xx 성공(200, 201) · 3xx Redirect(301, 302) · 4xx Client Error(400, 401, 403, 404) · 5xx Server Error(500, 502, 503).
HTTP와 HTTPS의 차이는?
HTTP는 평문 전송. HTTPS = HTTP + TLS → 암호화 + 서버 인증서로 신뢰성 검증. 현대 웹의 기본.
Stateless의 뜻, 장점, 단점은?
요청마다 독립, 서버는 이전 요청을 기억 안 함. 장점: 단순 → 확장성 · 효율↑. 단점: 로그인 등 상태 유지 → 쿠키 · 세션 · 토큰 필요.

    퀴즈 다 풀고 채점하기

    Q1www.naver.com을 입력했다. IP 주소를 얻기 위해 가장 먼저 확인하는 곳은?

    브라우저 캐시 → OS 캐시 → 리졸버.

    Q2게시판 10페이지로 이동하면 주소가 /models?p=10&sort=trending으로 바뀐다. 이 요청 방식과 장점은?

    ? 뒤 key=value는 GET. 페이지네이션은 GET.

    Q3HTTPS에 대한 설명으로 옳지 않은 것은?

    인증서는 서버가 발급받아 설치 · 보관해요.

    Q4Network 탭에서 bx-loader.gif 요청이 404였다. 가장 적절한 해석은?

    404 Not Found = 4xx 클라이언트 오류.

    Q5서버에서 잘못된 응답이 왔을 때 자주 보는 상태 코드는?

    5로 시작하면 서버 오류.

    Q6HTTP가 Stateless라서 생기는 일로 옳은 것은?

    요청마다 독립 → 상태는 따로. 단순해서 확장성은 오히려 높아요.

    Q7HTTP/1.1 200 OK · Content-Type: application/json · {"id":10}는 무엇인가?

    상태 코드가 있으면 응답. 200 = 성공, Body = JSON.

    내 말로 설명하기 면접 단골 1번

    "GET과 POST의 차이를 장단점과 함께 설명해 보세요."

    GET은 데이터를 URL 뒤에 ?key=value로 실어 보내고 보통 Body를 쓰지 않아요. 주소만으로 접근 · 공유 · 테스트가 쉬워 조회나 페이지네이션에 적합하지만, 데이터가 노출되므로 수정 작업에는 부적합해요. POST는 데이터를 Body에 담아 보내 주소창에 보이지 않으므로 로그인이나 데이터 생성처럼 노출되면 안 되는 요청에 적합하지만, 직접 접근 · 테스트가 어려워요. 그래서 무조건 하나를 쓰는 게 아니라 상황에 맞는 메서드를 고르는 게 정답이고, 실제 암호화는 메서드가 아니라 HTTPS(TLS)의 역할이에요.
