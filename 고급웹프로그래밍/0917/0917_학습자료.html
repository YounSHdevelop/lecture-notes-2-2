같은 this인데 어디서 부르냐에 따라 가리키는 게 다르다

this · 자기 참조 변수 · 화살표 함수의 Lexical this

객체 지향 언어엔 "나 자신"을 가리키는 키워드가 있어요. 자바 · C#은 this, 파이썬은 self. JavaScript도 this를 써요. 핵심은 하나예요. this는 함수가 어디에 선언됐는지가 아니라 어떻게 호출됐는지로 정해져요.

어디서 쓰나this가 가리키는 것
그냥 단독으로 (var x = this)window (브라우저의 최상위 객체)
전역에 만든 일반 함수 안지정 안 됨 → window
객체의 메서드 안 (person.fullName())그 메서드를 호출한 객체 (점 앞)
new로 만든 생성자 안새로 만들어진 객체
화살표 함수 안자기 this가 없음 → 바깥 스코프의 this를 그대로
교수님 예제 · 출력은?var num = 0;
function Add_Num() {
  this.num = 100;    // 전역 함수 → this = window → 전역 num을 100으로
  num++;             // 블록에 num 없음 → 스코프 체인으로 전역 num → 101
  console.log(num);              // 101
  console.log(window.num);       // 101
  console.log(num === window.num); // true (같은 변수)
}
Add_Num();

화살표 함수를 객체 메서드로 쓰면?

"철수"가 나올 것 같지만…const user = {
  name: "철수",
  sayHello: () => console.log(this.name)
};
user.sayHello();   // "철수" 아님! this = 바깥(window) → undefined

화살표 함수는 this를 만들지 않아서 바깥의 this(window)를 써요. 그래서 객체 메서드로는 부적합해요. 대신 콜백에선 이 성질을 오히려 역이용하기도 해요.

시험엔 이렇게

this는 호출 방식에 따라 결정된다: 단독 · 일반 함수 → window, 메서드 → 호출한 객체, 생성자(new) → 새 객체, 화살표 함수 → 자신의 this가 없고 외부 this 사용(Lexical this).

외우는 법: 밖은 윈도우 · 점 앞이 this · new는 새것 · 화살표는 바깥
바로 확인
const p = { first: "김", full() { return this.first; } }; p.full();에서 this는?
일반 함수 문법으로 만든 메서드라 점 앞의 p. 결과는 "김"이에요.

광고 차단 확장 프로그램은 어떻게 실행 중인 페이지를 바꿀까?

객체 · 프로퍼티 · 메서드 · 점 vs 대괄호 · 동적 변경

JavaScript의 객체는 여러 데이터를 키 : 값 쌍으로 담는 구조예요. 우리가 데이터를 주고받을 때 쓰는 JSON(JavaScript Object Notation)이 바로 이 모양이에요. 값엔 문자열, 숫자, 배열, 객체 뭐든 들어가고, 함수도 들어가요. 객체에 들어간 함수는 메서드, 나머지는 프로퍼티라고 불러요.

객체const user = {
  name: "Kim",                     // 프로퍼티
  age: 20,                         // 프로퍼티
  hello() { console.log("hello"); } // 메서드
};

꺼내는 법 두 가지

  • 점 표기법 user.name — 이름이 정해져 있을 때. 대부분 이거.
  • 대괄호 표기법 user[key] — 이름이 변수로 정해질 때. 반복문으로 컬럼을 하나씩 꺼낼 때처럼요.

실행 중에도 바뀐다

JS 객체의 가장 큰 특징은 실행 중에도 프로퍼티를 추가 · 변경 · 삭제할 수 있다는 거예요. user.email = "a@b.com"하면 바로 생기고, delete user.email하면 사라져요(true 반환, 이후엔 undefined).

교수님 예시 — 크롬 웹스토어의 애드블록 같은 확장 프로그램은, 지금 보고 있는 페이지의 객체 모델에 JS를 동적으로 끼워 넣어서 광고를 가려요. C나 자바로 만든 프로그램은 빌드 · 패키징이 끝나면 이렇게 중간에 끼워 넣기가 어렵죠. 이 유연함이 JS 객체의 특징이에요.
시험엔 이렇게

객체 = 키 · 값 쌍의 프로퍼티와 함수 형태의 메서드로 구성. 이름이 고정이면 점 표기법, 변수면 대괄호 표기법. 실행 중에도 추가 · 변경 · delete 가능.

외우는 법: 고정은 점 · 변수는 [ ]
바로 확인
const key = "age";일 때 user의 age를 꺼내는 올바른 방법은?
이름이 변수에 들어 있으면 대괄호. user.key는 "key"라는 이름의 프로퍼티를 찾아요.

user2의 이름을 바꿨는데 user1까지 바뀌었다. 왜?

원시 타입 vs 참조 타입 · 콜스택과 힙 · Call by Value / Reference

메모리 얘기예요. 함수를 호출할 때 쓰는 콜스택엔 주소와 값이 저장되는데, 타입에 따라 저장하는 게 달라요.

  • 원시 타입(숫자, 문자열, boolean…) — 콜스택에 값 자체를 저장. 복사하면 값이 새로 복사돼요 → 값 복사
  • 참조 타입(객체, 배열…) — 실제 데이터는 힙 메모리에 있고, 콜스택엔 그 주소만 저장. 복사하면 주소가 복사돼요 → 주소 복사
원시 타입: 값 복사let a = 10;
let b = a;     // 10이라는 값을 복사
b = 20;
console.log(a);  // 10 (a는 그대로)

참조 타입: 주소 복사const user1 = { name: "Kim" };
const user2 = user1;   // 주소를 복사 → 둘이 같은 객체를 가리킴
user2.name = "Lee";
console.log(user1.name); // "Lee" (같이 바뀜!)

이게 바로 Call by Value(값을 넘김)와 Call by Reference(주소를 넘김)의 차이예요. 교수님 말로 얕은 복사 · 깊은 복사, 원시 · 참조 타입, 메모리의 값 · 주소가 "다 엮여 있는 똑같은 얘기"예요. (6주차 React 객체 State 복사에서 그대로 다시 나와요.)

객체 비교도 주소로 한다

=== 는 타입까지 보는 엄격한 비교const a = { name: "Kim" };
const b = { name: "Kim" };
a === b   // false — 내용은 같아도 따로 만들어서 주소가 다름
const c = a;
a === c   // true — 같은 주소
교수님 비유 — 전국에 홍길동이 몇 명이나 있겠어요. 이름은 같아도 사는 곳(주소)이 다르고 주민번호도 다르죠.
시험엔 이렇게

원시 타입은 값을 복사(Value Copy), 참조 타입(객체)은 힙 메모리 주소를 복사(Reference Copy). 객체 ===는 주소를 비교하므로 내용이 같아도 따로 만든 객체는 false.

외우는 법: 원값 · 참주 (원시는 값, 참조는 주소) / 이름 같은 홍길동, 주소는 다르다
바로 확인
const arr1 = [1, 2]; const arr2 = arr1; arr2.push(3); 후 arr1은?
배열도 참조 타입이라 주소 복사. 같은 배열을 가리켜서 arr1도 [1, 2, 3].

똑같은 hello() 함수를 객체마다 만들 필요가 있을까?

Prototype · Prototype Chain · 생성자 함수 · ES6 class

user1, user2 객체에 구조도 같고 hello() 메서드도 똑같다면, 객체가 많아질수록 같은 함수가 메모리에 계속 반복 생성돼요. 교수님 말로 "컴퓨터공학자는 불필요한 걸 간소화하는 게 목표"예요. 그래서 공통 기능을 한 곳에 두고 같이 쓰자는 게 Prototype이에요.

Prototype은 다른 객체들이 프로퍼티와 메서드를 참조할 수 있게 해 주는 설계도 객체예요. 내 객체에서 찾는 게 없으면 Prototype에서 찾고, 거기도 없으면 그 Prototype의 Prototype에서 찾아요. 자바의 상속처럼 "상속의 상속"이 가능하죠. 이렇게 위로 올라가며 찾는 게 Prototype Chain이에요.

Scope Chain변수를 찾는다 · 블록 → 함수 → 전역으로 바깥으로
Prototype Chain프로퍼티 · 메서드를 찾는다 · 내 객체 → Prototype → 상위 Prototype으로 위로

생성자 함수 → ES6 class

생성자 함수 (이름은 대문자로 시작)function User(name, age) {
  this.name = name;
  this.age = age;
}
const user1 = new User("Kim", 20);  // 빈 객체가 먼저 생기고 this가 거기에 → return this 생략

ES6 class (2015)class User {
  constructor(name) { this.name = name; }
  hello() { console.log(`hi ${this.name}`); }
}

class는 가독성이 좋고 메서드를 구조 안에 명확히 쓸 수 있어요. 하지만 Prototype이 사라진 게 아니에요. class는 Prototype 구조를 쉽게 쓰라고 감싼 문법일 뿐이라, 자바 · C++의 class와 내부 동작이 같다고 생각하면 안 돼요.

교수
오버로딩이야 오버라이딩이야? 여기서 막히면 안 된다. 오버라이딩은 상속받은 메서드를 다시 정의하는 거고, 오버로딩은 매개변수를 바꿔 가면서 같은 이름의 함수를 늘리는 거예요. 객체지향 필수 개념이에요.9/17 강의 중 (말을 조금 다듬음)
시험엔 이렇게

Prototype = 객체들이 공통 프로퍼티 · 메서드를 공유하는 설계도 객체. Prototype Chain으로 위로 탐색. ES6 class는 Prototype 기반 문법(내부는 여전히 Prototype).

외우는 법: class = Prototype 포장지 / Scope는 바깥으로, Prototype은 위로
바로 확인

한 파일에 클래스 40개를 넣었더니 생긴 일

Module · export · import · default export · 모듈 스코프 · 순환 참조

클래스가 늘어나면 JS 파일 하나가 엄청 커져요. 그러면 Git으로 버전 비교하는 것도 오래 걸리고, 사람 머리는 다 비슷해서 변수 · 함수 이름이 충돌하고, 어떤 코드가 어떤 코드에 기대는지(의존 관계) 보기 어려워져요. 그래서 기능별로 파일을 나눠요(user, api, ui, utils…). 이렇게 나눈 독립적인 코드 단위가 Module이에요. 보통 JS 파일 하나가 모듈 하나예요.

math.js — 공개하기export const add = (a, b) => a + b;
export const sub = (a, b) => a - b;

main.js — 가져오기import { add, sub } from "./math.js";

User.js — 대표 하나만 (default)export default class User { … }

main.jsimport User from "./User.js";   // 중괄호 없이, 이름도 자유
  • named export — 여러 개 가능, 가져올 때 { } 안에 같은 이름으로. 필요한 것만 골라 가져올 수도 있어요.
  • default export — 모듈당 하나, 가져올 때 중괄호 없이 이름 자유. React 컴포넌트가 이 형태예요(10/1 실습의 export default function StudentCard).

export 안 하면 비밀 — 캡슐화

모듈은 자기만의 스코프를 가져서, 안에서 선언한 건 기본적으로 밖에서 못 봐요(private). 그래서 전역 변수가 줄고 이름 충돌도 막아요. 예를 들어 모듈 안의 apiKey는 export하지 않으면 다른 파일에서 import 자체가 안 돼요. 교수님은 API 키를 실수로 공개해서 사고 난 사례를 들며 "숨길 건 숨겨야 한다"고 했어요.

단, 모듈끼리 서로를 import하는 순환 참조(A가 B를, B가 A를)는 피해야 해요. 서로 핑퐁하다 로딩이 안 되고, 브라우저는 화면은 띄운 채 콘솔에만 에러를 쏟아내요.

시험엔 이렇게

Module = 관련 코드를 독립 단위로 분리, 자체 스코프로 캡슐화. export로 공개, import { 이름 } from "경로"로 가져옴. default export는 모듈당 하나, import 시 이름 자유.

외우는 법: 이름표는 { } · 대표는 하나 · 안 내보내면 비밀
바로 확인
counter.js가 export default function Counter() {…}로 내보냈다. main.js에서 올바르게 가져온 것은?
default는 중괄호 없이, 이름은 자유(MyCounter여도 OK). 중괄호는 named export용이에요.

① this ★ 실행 결과밖은 윈도우 · 점 앞 · new는 새것 · 화살표는 바깥

  • this = 호출 방식이 결정 · 단독 · 전역 함수 → window
  • 메서드 → 호출한 객체 · new → 새 객체 · 화살표 → 자기 this 없음(Lexical)

② 객체 고정은 점 · 변수는 [ ]

  • 프로퍼티(키 · 값) + 메서드(함수) · JSON 구조
  • 실행 중 추가 · 변경 · delete 가능 (애드블록)

③ 복사 · 비교 ★ 면접원값 · 참주

  • 원시 = 값 복사 / 객체 = 힙 주소 복사 → 한쪽 바꾸면 같이 바뀜
  • 객체 === = 주소 비교 · {name:"Kim"} === {name:"Kim"} → false

④ Prototype · class class = 포장지

  • Prototype = 공통 기능 공유 설계도 · Prototype Chain(위로) / Scope Chain(바깥으로)
  • 생성자 함수(대문자) + new → ES6 class(속은 Prototype)

⑤ Module 이름표는 { } · 대표는 하나

  • export / import { } from · default는 하나 · 이름 자유 (React 컴포넌트)
  • 모듈 스코프 = 기본 private → 캡슐화 · 순환 참조 ✗

빈칸 채우기 눌러서 정답 확인

this는 선언 위치가 아니라 호출 방식에 따라 정해지며, 메서드 안의 this는 메서드를 호출한 객체다. 화살표 함수는 자신의 this가 없어 외부 스코프의 this를 쓴다. 원시 타입은 값을, 객체는 주소를 복사한다. ES6 class는 Prototype 기반 문법이다. 모듈에서 기능을 공개하려면 export, 가져오려면 import를 쓴다.

플래시카드 알면 →, 모르면 ←

키보드: Space 뒤집기 · → 알아요 · ← 모르겠어요
this를 결정하는 것은?
선언 위치가 아니라 호출 방식.
메서드 안의 this와 전역 함수 안의 this는?
메서드 → 호출한 객체. 전역 함수 → window.
화살표 함수의 this는?
자신의 this가 없고 외부 스코프의 this를 그대로 씀(Lexical this). 객체 메서드엔 부적합.
점 표기법과 대괄호 표기법은 언제?
이름이 고정이면 점(user.name), 변수로 정해지면 대괄호(user[key]).
원시 타입과 참조 타입의 복사 차이는?
원시 = 값 복사(Value Copy). 참조(객체) = 힙 주소 복사(Reference Copy).
{name:"Kim"} === {name:"Kim"}의 결과와 이유는?
false. 따로 만든 객체라 주소가 다름. ===는 주소 비교.
Prototype이란?
객체들이 공통 프로퍼티 · 메서드를 공유하도록 하는 설계도 객체. JS 상속 구조의 핵심.
Prototype Chain vs Scope Chain은?
Prototype Chain = 프로퍼티 · 메서드를 위로 탐색. Scope Chain = 변수를 바깥으로 탐색.
ES6 class의 정체는?
Prototype 구조를 쉽게 쓰기 위한 문법(포장지). 내부는 여전히 Prototype.
named export와 default export의 차이는?
named: 여러 개, import { 같은 이름 }. default: 하나, 중괄호 없이 이름 자유.
모듈 스코프의 장점은?
안에서 선언한 건 기본 private → 전역 변수 감소, 이름 충돌 방지, 캡슐화.

    퀴즈 다 풀고 채점하기

    Q1브라우저에서 var x = this; console.log(x);의 결과는?

    단독으로 쓴 this는 최상위 객체 window.

    Q2교수님 예제 Add_Num()에서 console.log(num === window.num)의 결과는?

    this.num, num, window.num 모두 같은 전역 변수(101)라 true.

    Q3sayHello: () => console.log(this.name)를 객체 메서드로 넣고 호출하면 이름이 안 나온다. 이유는?

    Lexical this. 그래서 객체 메서드로는 일반 함수 문법을 써요.

    Q4let a = 10; let b = a; b = 20; 후 a의 값은?

    숫자는 원시 타입 → 값 복사 → a는 그대로 10.

    Q5const a = {n:1}; const b = {n:1}; const c = a;에서 옳은 것은?

    객체는 주소 비교. b는 따로 만들어 주소가 다르고, c는 a의 주소를 받았어요.

    Q6생성자 함수를 new로 호출할 때 일어나는 일로 옳은 것은?

    new → 새 공간 생성 → this 바인딩 → 자동으로 return this.

    Q7math.js에서 export const add = …로 내보낸 add를 main.js에서 가져오는 문장은?

    named export는 중괄호 안에 같은 이름으로. 1번은 default export일 때.

    내 말로 설명하기 면접 대비

    "Call by Value와 Call by Reference의 차이를 JavaScript 예시로 설명해 보세요."

    JavaScript에서 숫자 · 문자열 같은 원시 타입은 콜스택에 값 자체가 저장돼서, 다른 변수에 넣으면 값이 새로 복사돼요(Call by Value). 그래서 let b = a 후에 b를 바꿔도 a는 그대로예요. 객체 · 배열 같은 참조 타입은 실제 데이터가 힙에 있고 변수엔 그 주소가 저장돼서, 다른 변수에 넣으면 주소가 복사돼요(Call by Reference). 그래서 user2 = user1 후에 user2.name을 바꾸면 같은 객체를 가리키는 user1.name도 바뀌어요. 같은 이유로 내용이 같은 두 객체를 ===로 비교하면 주소가 달라서 false가 나와요.

    클래스 vs 클로저

    둘 다 상태와 동작을 묶어 쓰는 방식이에요. 객체를 통째로 묶어 여러 번 만들어야 하면 클래스, 특정 함수에 몇 가지만 얹어 전달할 땐 클로저가 편해요. 정답은 없고 상황에 맞게.

    React 프로젝트 폴더 구조

    src 아래에 components(UI), services(비즈니스 로직), models(데이터 구조 · 클래스), utils(공통 기능), api(백엔드 통신), 그리고 진입점 main. AI에게 React 프로젝트를 만들어 달라고 하면 거의 이 구조로 만들어요.

    오늘 배운 게 React에서 어떻게 쓰이나

    컴포넌트는 모듈 단위로 분리, props와 state는 객체로 관리, 이벤트 핸들러엔 클로저, 컴포넌트 조합엔 import/export.
