주소창에 naver.com을 치면 화면이 뜨기까지 무슨 일이 있을까?

2주차 · DNS · HTTP 요청/응답 · 상태 코드 · HTTPS · 렌더링

엔터 한 번 쳤을 뿐인데 1초 만에 화면이 떠요

그 1초 동안 브라우저는 "찾고 → 잇고 → 묻고 → 받고 → 그리는" 다섯 가지 일을 해요.

컴퓨터끼리는 이름(naver.com)이 아니라 숫자 주소(IP)로 찾아가요. 그래서 제일 먼저 이름을 IP로 바꾸는 일을 하는데, 이게 DNS Lookup이에요. 전화번호부에서 이름으로 번호를 찾는 거랑 같아요. (찾는 순서는 브라우저 캐시 → OS 캐시 → 리졸버, "브 · 오 · 리")

번호를 알았으면 전화를 걸어 연결해야겠죠. 이게 TCP 연결이고, https면 여기에 암호화 연결(TLS)까지 해요. 연결되면 "이 페이지 주세요"라는 HTTP Request를 보내고, 서버가 HTML · CSS · JS를 담은 Response를 돌려줘요.

요청서와 답장에는 뭐가 들어 있을까?

편지에 비유하면 쉬워요. 요청서에는 무엇을 할지(Method: GET · POST), 어디로(URL), 봉투에 적는 부가 정보(Header), 편지 내용(Body)이 들어가요. 답장은 "어떻게 됐는지"를 숫자로 먼저 알려 줘요. 그게 Status Code예요.

들어 있는 것외우는 법
RequestMethod · URL · Header · Body4개 (뭘 · 어디로 · 봉투 · 내용)
ResponseStatus Code · Header · Body3개 (결과 숫자 · 봉투 · 내용)

상태 코드는 첫 숫자만 보면 돼요. 2xx 성공, 3xx 다른 곳으로 가라(Redirect), 4xx는 요청한 쪽(Client) 잘못 — 404는 "그런 페이지 없어요"처럼 내가 주소를 잘못 친 경우죠. 5xx는 서버 잘못 — 500은 서버가 안에서 고장 난 거예요.

그냥 HTTP는 편지를 봉투 없이 보내는 거라 중간에 누가 다 읽을 수 있어요. 그래서 HTTPS = HTTP + TLS로 감싸요. TLS가 해 주는 건 세 가지: 암호화(못 읽게), 무결성(중간에 못 바꾸게), 인증(진짜 그 서버가 맞는지). "암 · 무 · 인".

파일을 받았으면 어떻게 그릴까?

받은 HTML은 그냥 글자예요. 브라우저가 이걸 읽어서(Parsing) 구조를 만들고 JS를 실행한 다음, HTML 구조와 CSS 스타일을 합쳐 Render Tree(화면에 실제로 보일 것들의 목록)를 만들어요. 그다음은 그림 그리는 순서랑 똑같아요.

시험엔 이렇게

URL 입력 → DNS Lookup으로 IP 확인 → TCP/TLS 연결 → HTTP Request 전송 → Server가 HTML · CSS · JS 반환 → Parsing · JS 실행 → Render Tree → Layout → Paint → Composite.

외우는 법: 찾고 · 잇고 · 묻고 · 받고 · 그린다 / 4xx는 내 탓, 5xx는 서버 탓 / TLS는 암 · 무 · 인

뭘 그릴지(Render Tree) 정했으면 먼저 어디에 얼마나 크게(Layout) 놓을지 정하고, 그다음에 색칠(Paint)해요. 밑그림 없이 색칠부터 할 순 없죠.

JS는 이미 뜬 화면을 어떻게 바꿀까?

2주차 · DOM · CSSOM · BOM(window · location · history · navigator)

버튼을 누르면 글씨가 빨개지는 페이지

JS가 HTML 파일을 직접 고치는 걸까요? 아니에요. 브라우저가 만들어 둔 "객체"를 고쳐요.

브라우저는 HTML을 읽어서 나무 모양 객체로 만들어 둬요. html 밑에 body, body 밑에 div… 이렇게요. 이게 DOM(Document Object Model)이에요. JS는 이 나무에서 원하는 가지를 찾아 고쳐요. 찾을 때 쓰는 게 querySelector예요. CSS 선택자 그대로 쓰면 돼요("#title", ".box").

글씨를 빨갛게 (CSS에 .active { color: red } 가 있음)const t = document.querySelector("#title");
t.classList.add("active");
  • querySelectorid가 title인 요소를 DOM 나무에서 찾아요.
  • classList.add그 요소에 active 클래스를 붙여요. 이때 바뀐 건 DOM뿐이에요.

여기서 교수님이 여러 번 물어본 게 "그럼 CSS(CSSOM)도 바뀌었어?"예요. 답은 그대로예요. CSS 쪽에는 원래부터 ".active면 빨강"이라는 규칙이 있었고, 요소에 그 이름표가 붙었을 뿐이에요. Render Tree를 다시 만들 때 그 규칙을 찾아 빨갛게 그리는 거죠.

DOM이 "페이지 안의 내용"이라면, BOM(Browser Object Model)은 페이지 밖, 브라우저 자체예요. 제일 위에 window(브라우저 창)가 있고 그 아래에 이런 것들이 달려 있어요.

객체뭘 알려 주나떠올리기
document지금 페이지 내용 = DOM페이지 안
location지금 주소(URL), 다른 주소로 이동주소창
history방문 기록, 뒤로 · 앞으로뒤로 가기 버튼
navigator브라우저 · 기기 정보"나 크롬이야"
시험엔 이렇게

DOM은 HTML 문서를 객체 기반 Tree로 표현하고 JS는 DOM으로 요소를 변경한다. DOM과 CSSOM이 결합해 Render Tree를 만든다. BOM은 window 아래 document · location · history · navigator 등 브라우저 환경 객체의 집합이다.

외우는 법: DOM은 페이지 안 · BOM은 브라우저 밖 / 주소창 location · 뒤로 가기 history · 기기 정보 navigator

선언하기도 전에 변수를 쓰면 어떻게 될까?

3주차 · Hoisting · TDZ · let/const · 객체 주소 복사 · 화살표 함수 this
교수
굉장히 굉장히 굉장히 중요한 개념, 호이스팅이 나옵니다. 프론트엔드 면접 질문을 검색해 보면 1~3번쯤에 "호이스팅이 뭐예요?"가 나와요.9/15 강의 중 (말을 조금 다듬음)

JS는 코드를 한 줄씩 실행하기 전에 한 번 쭉 훑어서 "이 범위에 어떤 변수 · 함수가 있지?"를 먼저 등록해 둬요. 그래서 선언이 위로 끌어올려진 것처럼 보이는데, 이걸 Hoisting이라고 해요. 중요한 건 등록만 하고 값은 아직 안 넣는다는 거예요. 그래서 키워드마다 결과가 달라요.

세 가지 상자로 보면 — var는 미리 만들어 둔 빈 상자라 열면 undefined가 나와요. let · const는 만들어 두긴 했는데 잠긴 상자라 선언 줄에 가기 전에 열면 에러가 나요(이 잠긴 구간이 TDZ). function 선언은 내용까지 다 들어간 꽉 찬 상자라 미리 불러도 잘 돌아가요.
출력 정답 ① Hoisting (3주차 p.19~21)console.log(a);
var a = 10;

console.log(b);
let b = 10;

hello();
function hello() {
  console.log("Hello");
}
  • console.log(a)a는 var라 빈 상자로 등록돼 있음 → undefined (10은 아직 안 들어감)
  • console.log(b)b는 let이라 잠긴 상자 → ReferenceError
  • hello()function 선언은 통째로 등록 → Hello (시험에선 문제마다 따로 묻는다고 생각하고 셋 다 알아 두기)

let과 const의 차이도 하나만 기억하면 돼요. 둘 다 같은 이름으로 다시 선언은 불가. 대신 let은 값을 바꿀 수 있고(재할당 가능), const는 못 바꿔요. 그리고 둘 다 { } 블록 안에서만 살아요(Block Scope). var는 블록을 무시해요.

객체를 다른 변수에 넣으면 복사될까?

숫자 · 문자열 같은 원시 타입은 대입하면 값이 복사돼요. 그런데 객체 · 배열은 크니까 변수에 객체 자체가 아니라 객체가 있는 주소가 들어 있어요. 그래서 대입하면 주소만 복사돼서, 두 변수가 같은 객체를 가리키게 돼요. 집 주소를 적은 쪽지를 복사해 준 거랑 같아요. 친구가 그 주소로 가서 벽지를 바꾸면 내 집 벽지가 바뀌죠.

출력 정답 ② 주소 복사 · 비교 (3주차 p.44~45)const user1 = { name: "Kim" };
const user2 = user1;
user2.name = "Lee";
console.log(user1.name);
const a = { name: "Kim" };
const b = { name: "Kim" };
console.log(a === b);
  • user2 = user1주소 복사 → 둘이 같은 객체를 가리킴
  • user1.nameuser2로 바꾼 게 그대로 보임 → Lee
  • a === b내용은 같아도 { }를 두 번 써서 객체가 2개 = 주소가 다름 → false (객체 ===는 주소 비교)

마지막으로 this. 일반 메서드 obj.say()에서 this는 점 앞의 객체예요. 그런데 화살표 함수는 자기 this가 없어서 바깥의 this를 그대로 써요. 객체 안에 화살표 함수로 메서드를 만들면 this가 그 객체가 아니라 바깥(브라우저에선 window)이라, this.name이 undefined가 나와요.

시험엔 이렇게

선언 전 접근 시 var는 undefined, let · const는 TDZ 때문에 ReferenceError, 함수 선언문은 호출 가능. 원시 타입은 값 복사, 객체는 주소(참조) 복사라 한쪽을 바꾸면 같이 바뀌고, 객체의 ===는 주소를 비교한다. 화살표 함수의 this는 바깥 this다.

외우는 법: 빈 상자 · 잠긴 상자 · 꽉 찬 상자 / 원시는 값, 객체는 주소
바로 확인
출력은?
const arr1 = [1];
const arr2 = arr1;
arr2.push(2);
console.log(arr1);
배열도 객체라 주소 복사예요. arr1 · arr2가 같은 배열이니 arr2에 넣은 2가 arr1에서도 보여요 → [1, 2].

setTimeout을 0초로 줬는데 왜 제일 늦게 찍힐까?

4주차 · Single Thread · Event Loop · 동기 → 마이크로 → 매크로 · Promise · fetch

setTimeout(() => console.log("B"), 0)

"0초 뒤에 실행해" 했으니 바로 찍힐 것 같죠? 실제로는 Promise보다도 늦게 찍혀요.

JS는 일하는 사람이 한 명(Single Thread)이에요. 한 번에 한 가지밖에 못 해요. 그래서 타이머 기다리기 같은 오래 걸리는 일은 브라우저(Web API)한테 맡겨 두고, 다 되면 "이거 실행해 줘" 하고 대기 줄에 세워 둬요. 그 줄을 지켜보다가 순서대로 넣어 주는 게 Event Loop예요.

핵심은 대기 줄이 두 개라는 거예요. Promise의 then이 서는 마이크로태스크 줄(급한 줄)과, setTimeout이 서는 매크로태스크 줄(일반 줄). 그리고 순서 규칙은 이것 하나예요.

식당으로 보면 — 요리사 한 명이 지금 받은 주문(동기 코드)을 끝까지 다 만들어요. 그게 끝나면 급한 쪽지함(마이크로 = Promise)을 빌 때까지 전부 처리하고, 그다음에야 일반 대기 손님(매크로 = setTimeout)을 한 명 받아요. setTimeout 0초는 "바로 해"가 아니라 "0초 뒤에 일반 줄에 서"라는 뜻이라서 늦어요.
출력 정답 ③ 출력 순서 (4주차 p.24)console.log("A");
setTimeout(() => {
  console.log("B");
}, 0);
Promise.resolve()
  .then(() => console.log("C"));
console.log("D");
  • 1단계 동기위에서부터 바로 실행되는 것만: A, D (B는 일반 줄로, C는 급한 줄로 보내 둠)
  • 2단계 마이크로급한 줄의 C
  • 3단계 매크로일반 줄의 B → 답 A D C B
출력 정답 ④ then 체인 (4주차 p.26)setTimeout(() => {
  console.log("Timeout");
}, 0);
Promise.resolve()
  .then(() => console.log("Promise1"))
  .then(() => console.log("Promise2"));
Promise.resolve()
  .then(() => console.log("Promise3"));
  • 처음 급한 줄Promise1, Promise3 (Promise2는 아직! 1이 끝나야 줄을 설 수 있음)
  • Promise1 실행 후그제야 Promise2가 급한 줄 맨 뒤에 섬 → 줄: Promise3, Promise2
  • 급한 줄 다 비움그다음에 Timeout → 답 Promise1 Promise3 Promise2 Timeout

Promise와 fetch는 이것만

Promise는 "나중에 결과를 주겠다"는 약속 객체예요. 상태는 세 가지: 아직 기다리는 중 Pending, 성공 Fulfilled, 실패 Rejected. 여러 개를 동시에 돌리고 전부 성공해야 성공으로 치려면 Promise.all을 써요.

fetch로 서버에 요청하면 Response가 오는데, 그 Body를 JS 객체로 바꾸려면 response.json()을 불러요. 함정 하나: 서버가 404 · 500을 줘도 fetch는 "답장은 받았으니까" 실패(reject)로 안 쳐요. 네트워크가 끊겼을 때만 reject예요. 그래서 성공 여부는 response.ok(200번대면 true)로 직접 확인해야 해요.

시험엔 이렇게

JS는 Single Thread로 실행되고 Event Loop가 콜백 실행 시점을 관리한다. 실행 순서는 동기 코드 → 마이크로태스크(Promise) 전부 → 매크로태스크(setTimeout). fetch는 HTTP 에러여도 reject되지 않으므로 response.ok로 확인한다.

React는 사실 이 개념이 거의 끝이에요. useEffect랑 useState 잘 쓰고, 컴포넌트 어떻게 쪼개고, 리렌더링 언제 일어나는지, 그것만 잘하면 거의 끝이거든요.10/8 강의 중 (말을 조금 다듬음)

React 컴포넌트에서 바뀌면 화면도 다시 그려야 하는 값을 State라고 해요. const [count, setCount] = useState(0)처럼 쓰면 [지금 값, 바꾸는 함수] 두 개를 돌려줘요. 일반 변수(let n)를 바꾸면 React가 몰라서 화면이 안 바뀌고, setCount로 바꿔야 React가 알아채고 다시 그려요(Re-render).

그런데 State는 Snapshot, 즉 그 렌더링 순간에 찍힌 사진이에요. 이번 렌더링 안에서 count는 계속 같은 숫자로 고정돼 있어요. setCount를 불러도 지금 사진이 바뀌는 게 아니라 "다음 렌더링에 이 값으로 해 줘"라고 예약하는 거예요.

출력 정답 ⑤ Snapshot (6주차) · 지금 count = 1setCount(count + 1);
setCount(count + 1);
setCount(count + 1);
  • 세 줄 모두사진 속 count는 계속 1 → 셋 다 "1 + 1 = 2로 해 줘"
  • 다음 렌더"2로" 세 번 = 그냥 2
대신 이렇게 세 번 쓰면? · 지금 count = 1setCount(prev => prev + 1);
setCount(prev => prev + 1);
setCount(prev => prev + 1);
  • prev =>사진 값이 아니라 바로 앞 결과를 받아서 계산(Functional Update) — 릴레이 바통처럼
  • 계산1 → 2 → 3 → 4

useEffect는 언제 실행될까?

컴포넌트에도 일생이 있어요(Lifecycle): 처음 화면에 나타나는 Mount → State · Props가 바뀌어 다시 그려지는 Update → 화면에서 사라지는 Unmount. useEffect는 화면을 그린 뒤에 할 일(타이머, API 요청 같은 Side Effect)을 적는 곳이고, 두 번째 인자(Dependency Array)로 언제 실행할지 정해요.

두 번째 인자실행 시점
없음 useEffect(fn)렌더링될 때마다 매번
빈 배열 useEffect(fn, [])Mount 때 딱 1번
useEffect(fn, [count])Mount 때 + count가 바뀔 때마다

Effect 안에서 return () => { … }로 돌려준 함수가 Cleanup이에요. Unmount될 때 실행돼서 켜 둔 타이머를 꺼 줘요.

useReducer는 뭐가 다를까?

State 바꾸는 규칙이 많아지면(증가 · 감소 · 초기화 · 특정 값으로…) setter를 여기저기 부르기 복잡해져요. 그래서 바꾸는 규칙을 reducer 함수 한 곳에 모아 두고, 화면에서는 "이거 해 줘"라는 쪽지(action)만 보내요. 그 보내는 함수가 dispatch예요. 그래서 반환값도 [state, setState] 대신 [state, dispatch]예요.

출력 정답 ⑥ dispatch (7주차) · 처음 { count: 0 }dispatch({ type: "INCREMENT" });
dispatch({ type: "INCREMENT" });
dispatch({
  type: "SET_COUNT",
  payload: 10,
});
dispatch({ type: "DECREMENT" });
  • INCREMENT ×20 → 1 → 2
  • SET_COUNT 10더하기가 아니라 payload 값 그대로 → 10
  • DECREMENT10 → 9 (모르는 type이 오면 default로 state 그대로)
시험엔 이렇게

State는 렌더링 시점의 Snapshot이라 이전 값에 의존하면 setCount(prev => prev + 1)처럼 Functional Update를 쓴다. useEffect는 Render 이후 실행되고 Dependency Array로 실행 시점이 정해지며([]는 Mount 때 1번), Cleanup은 Unmount 때 실행된다. useReducer는 [state, dispatch]를 반환하고, dispatch로 보낸 action을 reducer가 받아 새 state를 반환한다.

외우는 법: count는 사진(2) · prev는 릴레이(4) / 없으면 매번 · 비면 처음만 · 넣으면 바뀔 때 / setter 대신 dispatch
✗ 이렇게 생각하면 틀려요setCount(count + 1)을 세 번 부르면 3 올라간다
○ 맞는 생각세 번 다 같은 사진 값으로 계산해서 1만 올라간다. 이어서 올리려면 prev.
바로 확인
count가 0일 때 아래를 실행했다. 다음 렌더의 count는?
setCount(count + 5);
setCount(prev => prev + 1);
첫 줄은 사진 값 0으로 "5로 해 줘". 둘째 줄은 앞 결과(5)를 받아서 +1 → 6.
바로 확인
useEffect(() => console.log("E"), [])가 있는 컴포넌트가 Mount된 뒤 State가 3번 바뀌었다. "E"는 몇 번 찍힐까?
빈 배열 = Mount 때 딱 1번. 이후 Update가 몇 번 일어나도 다시 실행 안 해요.

내 말로 설명하기 주관식 대비

"console.log A · setTimeout B · Promise C · console.log D의 출력이 왜 A D C B인지 설명해 보세요."

JS는 Single Thread라 먼저 동기 코드를 끝까지 실행해서 A와 D를 찍어요. setTimeout의 콜백은 0초여도 매크로태스크 큐로, Promise의 then 콜백은 마이크로태스크 큐로 보내져요. 동기 코드가 끝나 Call Stack이 비면 Event Loop가 마이크로태스크를 먼저 전부 실행해서 C를 찍고, 그다음 매크로태스크인 B를 찍어요. 그래서 A D C B예요.
