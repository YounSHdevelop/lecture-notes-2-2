"아키텍처 설계는 사람이 해야 한다" — 그게 정확히 뭘 하라는 걸까?

React Architecture · 컴포넌트 · State · Props · 이벤트 · 컴포넌트 트리 · Presentational / Container

스프링은 MVC, 안드로이드는 MVVM처럼 정해진 구조가 있어요. 그런데 React는 정해진 아키텍처를 주지 않아요. 자유도가 높은 대신, 앱이 커질수록 컴포넌트 · State · Props · 이벤트 이 네 가지를 어떻게 엮을지 직접 고민해야 해요.

모든 아키텍처의 목적은 같아요. UI, 비즈니스 로직, 서버 통신을 잘 나눠서 서로에게 주는 영향을 최소로 만드는 것. React에서는 UI는 컴포넌트로, 비즈니스 로직은 별도 JavaScript 파일로, 서버 통신은 useEffect로 나눠요. 교수님이 한 줄로 정리한 핵심은 이거예요.

컴포넌트 트리, 그리고 두 종류의 컴포넌트

React 앱은 컴포넌트가 컴포넌트를 품는 컴포넌트 트리예요. 트리는 UI 구조이면서 동시에 데이터가 어디서 어디로 흐르는지를 보여 주는 지도예요. 컴포넌트를 너무 크게 만들면 state가 많아지고, 하나 고치면 엉뚱한 데가 깨져요(사이드 이펙트). 그래서 작은 역할 단위로 나눠요. 예전부터 쓰던 개념적인 구분이 두 가지 있어요.

React는 MVC · MVVM 같은 정해진 아키텍처를 강제하지 않으며, 컴포넌트 · State · Props · 이벤트를 어떻게 연결할지가 설계의 핵심이다. 아키텍처 설계의 목적은 UI, 비즈니스 로직, 통신을 분리해 서로의 영향을 최소화하고 데이터가 어디서 생성되어 어디로 흐르는지를 명확하게 만드는 것이다.

장면 2

데이터는 아래로 내려가는데, 자식 버튼을 누른 건 어떻게 부모가 알까?

단방향 데이터 흐름 · Props는 읽기 전용 · 콜백 Props · 이벤트는 위로 · State 위치 · Lifting State Up

복습부터. Props는 부모가 자식에게 데이터를 넘기는 통로이고, 자식은 받은 Props로 UI를 그려요. Props는 읽기 전용이라 고치지 않아요. 데이터가 한 방향(위 → 아래)으로만 흐르니까, 값이 이상하면 "어디서 바뀌었지?"를 추적하기 쉬워요.

그럼 자식에서 일어난 이벤트는? 부모가 만든 함수를 Props로 내려 주고, 자식은 그 함수를 호출만 해요. 이걸 콜백 Props라고 해요. 함수(구현체)는 내려가지만, 호출 결과(값)는 부모까지 올라와요.

콜백 Props · 자식에서 고른 id가 부모까지 올라온다function Parent() {
  const handleSelect = (id) => console.log("선택:", id);   // 부모가 핸들러를 정의
  return <Child id={7} onSelect={handleSelect} />;        // 함수를 Props로 내려 줌
}
function Child({ id, onSelect }) {
  return <button onClick={() => onSelect(id)}>고르기</button>;  // 호출만 한다
}
// 버튼 클릭 → 콘솔: 선택: 7

State는 어디에 둘까 — Lifting State Up

State는 실제로 쓰는 컴포넌트, 또는 그에 가장 가까운 곳에 둬요. 한 컴포넌트만 쓰면 로컬 state. 형제 두 컴포넌트가 같은 state를 써야 하면 공통 부모로 끌어올려요(Lifting State Up). 그러면 부모가 그 state의 원천(Single Source of Truth)이 되고, 자식은 Props로 받아 쓰고, 바꾸고 싶으면 콜백으로 부모의 세터를 불러요. 모든 state를 최상위에 올릴 필요는 없어요. 범위가 넓을수록 하나만 바뀌어도 다시 그려지는(리렌더링) 컴포넌트가 많아지거든요. (자료 Summary에는 공유 State를 관리하는 방법으로 Lifting State Up과 함께 Context도 이름만 나와요. 수업에서 따로 다루진 않았어요.)

시험엔 이렇게

React의 데이터는 부모에서 자식으로 Props를 통해 한 방향으로 전달되며(One-way data flow), Props는 읽기 전용이다. 그래서 데이터 흐름이 예측 가능하고, 상태 변경 위치를 추적하기 쉬워 디버깅이 쉽다. 자식의 이벤트는 부모가 내려 준 콜백 Props를 호출해 부모로 전달된다. State는 실제로 사용하는 컴포넌트에 최대한 가깝게 두고, 여러 자식이 공유하면 공통 부모로 끌어올린다(Lifting State Up). 공유 State는 Lifting State Up, Context 등으로 관리할 수 있다.

창 크기를 알아야 하는 컴포넌트가 열 개라면, useEffect를 열 번 쓸까?

커스텀 훅 · useWindowWidth · 이름은 use로 시작 · 로직 재사용 · 서비스 레이어(userApi.js) · 테스트 용이성

state와 effect로 같은 일을 여기저기서 반복하면 useEffect가 "덕지덕지" 붙어요. 그 반복되는 로직을 함수 하나로 묶은 게 커스텀 훅이에요. 수업 예제는 브라우저 창의 너비를 알려 주는 훅이었어요.

커스텀 훅 · useWindowWidthfunction useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);      // 처음 값 = 지금 창 너비
  useEffect(() => {
    const handler = () => setWidth(window.innerWidth);        // 창 크기가 바뀌면 state 갱신
    window.addEventListener("resize", handler);               // 마운트 때 한 번 등록 ([] 의존성)
    return () => window.removeEventListener("resize", handler);  // 언마운트 때 정리
  }, []);
  return width;                                               // UI가 아니라 값(로직의 결과)을 돌려줌
}

// 쓰는 쪽: 한 줄이면 끝
const width = useWindowWidth();

컴포넌트가 화면(UI)을 재사용하는 단위라면, 커스텀 훅은 UI가 아닌 로직을 재사용하는 단위예요. 이름은 항상 use로 시작해요(useState, useEffect, useReducer와 통일). 훅 하나만 고치면 이걸 쓰는 모든 컴포넌트에 반영되니 유지 보수가 쉬워요.

서비스 레이어 — API 호출은 따로 빼 둔다

API 호출 코드를 컴포넌트 안에 다 넣으면 복잡해지죠. 그래서 .jsx가 아닌 그냥 .js 파일에 API 함수들을 모아 둬요.

userApi.js · 서비스 레이어export async function getUsers() {
  const response = await fetch("/api/users");   // 응답 올 때까지 기다렸다가
  return response.json();                       // JSON으로 바꿔서 돌려줌
}
// 컴포넌트에서는 useEffect 안에서 getUsers()만 호출해 state에 넣으면 끝

이렇게 두면 재사용성이 높아지고, 테스트하기 쉬워져요. 비즈니스 로직에 붙이기 전에 API 함수만 따로 불러서 원하는 데이터가 오는지 확인할 수 있거든요. 현업에서는 백엔드가 준 API 명세대로 이런 함수(엔드포인트 연결)를 먼저 쭉 만들어 두고, 필요한 컴포넌트가 가져다 써요.

시험엔 이렇게

커스텀 훅은 반복되는 state · effect 로직을 하나의 함수로 묶어 재사용하는 것으로, UI가 아닌 로직을 재사용하며 이름은 use로 시작한다. API 호출은 서비스 레이어(별도 JS 파일)로 분리해 컴포넌트의 복잡도를 낮추고 재사용성 · 테스트 용이성을 높인다.

좋아요 +1, −1, 리셋, 10으로 맞추기 — 세터 대신 dispatch 하나로

useReducer · reducer(state, action) · dispatch · action type · payload · 새 state 반환(순수 함수) · useState와 비교

10/1의 좋아요 카운터를 떠올려 봐요. +1, 취소(−1), 리셋(0), 특정 값으로 설정… 상태를 바꾸는 방법이 늘어날 때마다 세터를 부르는 함수가 여기저기 흩어져요. 이걸 한 곳에 모으자는 게 useReducer예요. 여러 개의 state 변경 로직을 하나의 함수(reducer)로 관리하는 훅이에요.

useReducer · 카운터 (자료 p.15~16 코드 + 수업에서 말한 RESET)function reducer(state, action) {            // (현재 state, 무엇을 할지) → 새 state
  switch (action.type) {
    case "INCREMENT": return { ...state, count: state.count + 1 };
    case "DECREMENT": return { ...state, count: state.count - 1 };
    case "RESET":     return { ...state, count: 0 };
    case "SET_COUNT": return { ...state, count: action.payload };  // 추가 데이터는 payload로
    default:          return state;
  }
}

function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });   // 세터 대신 dispatch
  return (
    <>
      <p>{state.count}</p>
      <button onClick={() => dispatch({ type: "INCREMENT" })}>+1</button>
      <button onClick={() => dispatch({ type: "SET_COUNT", payload: 10 })}>10으로</button>
    </>
  );
}
  • useReducer(reducer, 초기 state) — useState와 달리 reducer라는 인자가 하나 더 있고, 돌려받는 건 [state, dispatch]예요.
  • action — 어떤 변경을 할지 설명하는 객체. type이 "무엇을"(키워드), payload가 "얼마로" 같은 추가 데이터.
  • dispatch — 세터를 직접 부르지 않고 action을 보내요. 그러면 reducer가 type에 맞는 분기를 타서 새 state를 만들고, 리렌더링이 일어나요.
  • 가장 큰 장점 — 기존 state를 직접 고치지 않고 ...state(스프레드)로 새 객체를 만들어 반환해요. 그래서 reducer는 가능하면 순수 함수로 작성하는 게 좋아요.

흐름과 실행 결과

이벤트 발생 → dispatch(action) → reducer(state, action)가 분기 → 새 state 반환 → 리렌더링. 초기 count가 0일 때 INCREMENT, INCREMENT, DECREMENT를 차례로 보내면 0 → 1 → 2 → 1. 그다음 SET_COUNT(payload 10)를 보내면 10, RESET이면 0이에요. 자료 p.16의 흐름 그림 그대로 User Event → dispatch(action) → Reducer → New State → Re-render예요.

시험엔 이렇게

useReducer는 복잡한 state 변경 로직을 하나의 reducer 함수에서 관리하는 훅이다. UI에서는 세터 대신 dispatch로 어떤 변경이 필요한지 action(type, payload)을 전달하고, reducer는 현재 state와 action을 받아 기존 state를 직접 수정하지 않고 새로운 state를 반환한다. 변경 규칙을 한곳에 모아 가독성과 유지 보수성이 좋아지며, 단순한 상태는 useState, 복잡한 상태는 useReducer가 적합하다.

외우는 법: dispatch로 보내고, reducer가 새로 만들어 돌려준다 · 간단하면 State, 규칙 많으면 Reducer

○ 맞는 생각기존 state는 그대로 두고 { ...state, count: state.count + 1 }처럼 새 객체를 반환

★ 시험 범위 마지막 수업

① 아키텍처

  • React 아키텍처 : 정해진 패턴 없이 컴포넌트 · State · Props · 이벤트를 연결하는 설계. 목적은 UI · 로직 · 통신 분리
  • Container / Presentational : 데이터를 만드는 위쪽 컴포넌트 / Props로 그리기만 하는 아래쪽 컴포넌트

② 데이터 흐름 데이터는 아래로, 이벤트는 위로

  • One-way data flow : 부모 → 자식으로 Props 전달, Props는 읽기 전용
  • 콜백 Props : 부모 함수를 내려 주고 자식이 호출 → 이벤트가 부모로
  • Lifting State Up : 여러 자식이 쓰는 state를 공통 부모로. state는 쓰는 곳 가까이

③ 분리

  • 커스텀 훅 : 반복되는 state · effect 로직을 묶어 재사용(useWindowWidth). 이름은 use~
  • 서비스 레이어 : API 호출을 별도 JS 파일로 분리 → 재사용성 · 테스트 용이성
  • UI State / Server State : 화면 안의 상태(모달 · 토글 · 입력) / 서버에서 온 데이터(무결성, API로 갱신)

④ useReducer ★ 실행 결과

  • useReducer : 복잡한 state 변경 로직을 reducer 하나에 모으는 훅. [state, dispatch] = useReducer(reducer, 초기값)
  • dispatch : 세터 대신 action({ type, payload })을 보냄
  • reducer : (state, action) → 새 state. 기존 state를 고치지 않음(스프레드, 순수 함수)
  • 간단하면 useState, 변경 규칙이 많으면 useReducer

빈칸 채우기 눌러서 정답 확인

React에서 데이터는 부모에서 자식으로 Props를 통해 한 방향으로 흐르고, 자식의 이벤트는 부모가 내려 준 콜백 Props를 호출해 위로 전달된다. 여러 자식이 같은 state를 쓰면 공통 부모로 옮기는데 이를 Lifting State Up이라 한다. 반복되는 로직을 묶어 재사용하는 함수는 커스텀 훅이며 이름은 use로 시작한다. useReducer에서 UI는 세터 대신 dispatch로 action을 보내고, reducer는 현재 state와 action을 받아 새로운 state를 반환한다.

React 아키텍처 설계의 핵심을 한 줄로?
데이터가 어디서 생성되고, 어디서 관리되고, 어디로 흐르는지를 명확하게 만드는 것.
Presentational vs Container 컴포넌트?
Presentational은 Props를 받아 UI만 그림. Container는 state · API 호출 · 데이터 처리를 맡고 Props로 내려 줌.
Props의 성질 두 가지?
부모 → 자식 한 방향 전달, 읽기 전용(고치지 않음).
자식의 이벤트를 부모에게 알리는 방법은?
부모가 핸들러 함수를 Props(콜백 Props)로 내려 주고, 자식이 그 함수를 호출한다.
Lifting State Up이란?
두 자식이 같은 state를 써야 할 때 state를 공통 부모로 옮기는 것. 부모가 원천이 됨.
커스텀 훅이란?
반복되는 state · effect 로직을 함수로 묶어 재사용하는 것. UI가 아닌 로직 재사용, 이름은 use로 시작.
서비스 레이어를 두는 이유는?
API 호출을 별도 JS 파일로 분리해 컴포넌트 복잡도를 줄이고 재사용성 · 테스트 용이성을 높이려고.
UI State와 Server State의 예는?
UI: 모달 열림, 토글, 입력값, 타이머. Server: 서버에서 받은 회원 · 상품 목록.
useReducer의 반환값과 인자는?
const [state, dispatch] = useReducer(reducer, 초기 state).
action 객체의 type과 payload는?
type = 어떤 변경을 할지(키워드), payload = 변경에 필요한 추가 데이터.
reducer의 가장 큰 장점은?
기존 state를 직접 수정하지 않고 새 state를 반환하며, 변경 로직이 한곳에 모인다.
useState와 useReducer는 언제 쓰나?
단순한 상태(토글 · 카운터)는 useState, 변경 규칙이 많은 복잡한 상태(폼 · 장바구니 · 투두)는 useReducer.

    기존 state를 고치지 않고 새 state를 돌려주는 것이 reducer의 가장 큰 장점이에요. 10/6의 "state는 새 값으로 교체" 원칙과 같아요.
