장면 1

콘솔엔 값이 바뀌었는데 화면은 그대로다

State 정의 · 일반 변수 vs State · 이벤트가 시작점
일반 변수로 하면let count = 0;
count++;     // 콘솔로 찍으면 1. 그런데 화면은 0 그대로!

값은 바뀌었어요. 그런데 React가 그걸 감지하지 못해서 렌더링이 안 일어나요. 교수님 말로 "이게 제일 큰 문제"예요. 그래서 화면에 영향을 주는 값은 State로 만들어요. State가 바뀌면 그게 React한테 "UI를 다시 계산해야 해"라는 신호가 되거든요. 화면과 상관없이 내부적으로만 들고 있는 값은 일반 변수로 둬도 돼요.

그리고 State는 보통 사용자 행동에서 바뀌어요. 웹페이지는 한번 뜨고 나면 내가 클릭 · 입력 · 제출을 해야 화면이 바뀌잖아요. 그래서 이벤트 핸들러(onClick, onChange, onSubmit) 안에서 setter를 불러요.

복습 — useStateconst [count, setCount] = useState(0);
// count: 현재 State · setCount: 변경 함수(setter) · 0: 초깃값
// useState는 둘을 배열로 돌려주고, 배열 구조 분해 할당으로 받는다

setCount(count + 1);   // ○ Correct
count = count + 1;     // ✗ Incorrect — React가 모름
시험엔 이렇게

State = UI를 결정하는 변경 가능한 데이터. 일반 변수는 값이 바뀌어도 React가 감지하지 못해 리렌더링되지 않으므로, 화면에 영향을 주는 값은 State로 관리하고 반드시 Setter로 변경한다.

외우는 법: 변수는 조용히 바뀌고, State는 React에 신호를 보낸다
바로 확인
버튼 클릭마다 let n = 0;의 n을 n++ 한다. 화면의 {n}은?
일반 변수는 React가 감지 못 해서 리렌더링이 없어요. 화면은 그대로.

장면 2

setter를 부르면 컴포넌트 함수가 처음부터 다시 돈다

Re-render · Render 단계 · Commit 단계 · Layout / Paint

Re-render는 결국 컴포넌트 함수가 다시 실행되는 것이에요. 컴포넌트는 JSX를 return하는 함수니까, 다시 실행되면 새 JSX가 나오죠.

클릭할 때마다 콘솔엔?function Counter() {
  console.log("render");               // 리렌더링마다 매번 찍힌다
  const [count, setCount] = useState(0);  // 그렇다고 0으로 초기화되진 않는다
  return <h1>{count}</h1>;
}

"함수가 처음부터 다시 실행되면 useState(0)도 다시 0이 되는 거 아냐?" 싶죠. 아니에요. 컴포넌트가 한번 State를 들고 있으면 React가 그 값을 기억하고 있다가 돌려줘요.

렌더링은 두 단계

단계하는 일
Render컴포넌트를 실행해 새 UI 구조 계산 → 이전 결과(Virtual DOM)와 비교 → 바꿀 곳 결정
Commit필요한 DOM 변경만 실제 브라우저에 반영 → 브라우저가 Layout · Paint로 화면 표시

그래서 Re-render가 일어났다고 실제 DOM 전체가 다시 만들어지는 게 아니에요. 바뀐 부분만. 대신 메모리를 좀 더 먹는 게 단점이라고 했죠.

시험엔 이렇게

Setter 호출 → React가 새 State 반영 준비 → 컴포넌트 함수 재실행(Re-render) → 새 JSX 계산 → 이전 결과와 비교 → 필요한 DOM만 반영. 렌더링은 Render 단계(계산 · 비교)와 Commit 단계(실제 DOM 반영)로 나뉜다.

외우는 법: Render = 계산 · Commit = 반영(그리기)
바로 확인
위 Counter에서 버튼으로 setCount를 3번(클릭 3번) 실행했다. 처음 렌더링 포함 "render"는 콘솔에 몇 번?
처음 1번 + 클릭마다 리렌더링 3번 = 4번. (개발 모드 StrictMode에선 더 찍힐 수 있어요 — 10/8 참고)

장면 3

count가 1일 때 setCount(count + 1)을 3번 부르면? (실행 결과 문제)

State == Snapshot · Multiple Updates · Functional Update

교수님이 강의실에서 물어봤어요. 다들 "4"라고 했죠. 정답은 2예요.

count가 1일 때function update_count() {
  setCount(count + 1);   // 1 + 1 → "2로 해 줘"
  setCount(count + 1);   // count는 여전히 1 → 또 "2로 해 줘"
  setCount(count + 1);   // 또 "2로 해 줘"
}                        // 결과: 2

왜냐면 State는 스냅샷(사진)이에요. 한 번의 렌더링 안에서 State 값은 그 시점에 찍힌 사진처럼 고정돼 있어요. setter를 불러도 지금 실행 중인 코드의 count가 즉시 바뀌지 않고, 새 값은 다음 렌더링에서 쓸 수 있어요.

그래서 이것도console.log(count);   // 0
setCount(count + 1);
console.log(count);   // 여전히 0

4로 만들려면 — Functional Update

setter에 함수를 넘긴다setCount(prev => prev + 1);   // 1 → 2
setCount(prev => prev + 1);   // 2 → 3 (prev = 이전 업데이트 결과)
setCount(prev => prev + 1);   // 3 → 4  결과: 4

prev는 이전 업데이트의 결과를 받아요. 그래서 순서대로 쌓여요. 10/1 실습에서 AI가 써 준 prev => prev + 1이 바로 이거예요. 이전 State에 기대서 새 State를 계산할 때(카운터, 토글, 큐 처리) 권장되는 방식이에요.

틀린 생각setCount를 부른 다음 줄에서 count는 이미 바뀌어 있다
맞는 생각State는 스냅샷. 새 값은 다음 렌더링에서 보인다
시험엔 이렇게

State는 각 렌더링 시점의 Snapshot이라 Setter를 호출해도 현재 코드의 값은 즉시 바뀌지 않는다. 같은 렌더에서 setCount(count + 1)을 여러 번 호출하면 모두 같은 count를 참조하므로, 이전 값에 의존하는 연속 업데이트는 setCount(prev => prev + 1) 형태의 Functional Update를 쓴다.

외우는 법: count는 사진 · prev는 릴레이 (1 → +1 ×3: 사진이면 2, 릴레이면 4)
바로 확인
count가 0일 때 setCount(prev => prev + 1); setCount(count + 1);을 실행하면 최종 count는?
첫 줄로 1이 되지만, 두 번째 줄의 count는 스냅샷 0 → "1로 해 줘". 최종 1.

장면 4

user.age = 21 하면 왜 안 되고, 새 객체를 만들어야 할까? (면접 단골)

여러 State · Object State · Spread · 얕은 복사 · Immutability · Derived State

컴포넌트 하나에 State가 하나일 수는 없어요. 이름 · 나이 · 활성화 여부처럼 의미가 다르면 각각의 State로 나누고, 각자 자기 setter로 바꿔요. 관련 없는 값을 억지로 한 객체에 묶을 필요는 없어요. "여기서부터 갑자기 설계가 나온다"고, 단순하고 명확하게 짜는 게 제일 중요하대요.

State엔 객체도 넣을 수 있어요. 대신 속성을 직접 바꾸면 안 돼요. 기존 객체를 바탕으로 새 객체를 만들어 바꿔치기해요.

Object State — Immutable Updateconst [user, setUser] = useState({ name: "Kim", age: 20 });

user.age = 21;                       // ✗ 직접 수정
setUser({ ...user, age: 21 });       // ○ 펼쳐서 복사 + age만 덮어쓰기

Array State도 같다const [items, setItems] = useState([]);
setItems([...items, newItem]);      // push 대신 새 배열

Spread와 얕은 복사 — 주소로 보기

3주차에 배운 "객체 ===는 주소 비교"가 여기서 그대로 쓰여요. Spread는 얕은 복사(Shallow Copy)라 새 객체를 만들지만 한 단계만 복사해요. 객체 안에 객체가 또 있는(중첩) State라면 바뀌는 안쪽 객체까지 각각 펼쳐 복사해야 해요.

교수님 예시 — 불변 객체(Immutable) — 대부분 언어의 String은 불변 객체예요. a = "a" 다음에 a += "b" 하면 결과는 "ab"지만, 메모리로 보면 원래 0x001의 "a"를 고친 게 아니라 0x002에 "ab"가 새로 생긴 거예요. React의 객체 State도 이렇게 "고치지 말고 새로 만들어" 써요.

왜 굳이? setter로만 바꾸면 어디서 바꿨는지 추적이 쉽고, 새 객체를 만들면 이전 값과 새 값이 명확히 구분돼서 React의 변경 감지와 예측 가능한 렌더링에 유리해요.

계산할 수 있으면 State로 만들지 마 — Derived State

Derived Stateconst [price, setPrice] = useState(10000);
const [quantity, setQuantity] = useState(2);
const total = price * quantity;   // State 아님! 리렌더링 때마다 자동 재계산

total까지 State로 두면 같은 데이터를 중복 저장해서 동기화 문제가 생길 수 있어요. 원본 State만 저장하고 나머지는 계산하면 데이터 흐름이 단순해져요.

시험엔 이렇게

Object · Array State는 직접 수정하지 않고 Spread Operator(...)로 복사한 새 객체 · 배열을 만들어 Setter로 교체한다(Immutable Update). Spread는 얕은 복사라 중첩 객체는 각 계층을 따로 복사해야 한다. 다른 State로 계산 가능한 값은 State로 만들지 않는다(Derived State).

외우는 법: 고치지 말고 펼쳐서 새로 / 계산되면 State 아님
바로 확인
const newUser = { ...user }; 후 user === newUser와 user.name === newUser.name의 결과는?
새 객체라 주소가 달라 false, name은 같은 값이 복사돼서 true.

두 자식이 같은 값을 써야 하면 State는 누가 들고 있어야 할까?

Lifting State Up · Callback Props · Prop Drilling · Controlled Component · Props vs State

기본은 그 데이터를 필요로 하는 컴포넌트가 State를 들고 있는 거예요. 그런데 Child A와 Child B가 같은 State를 필요로 하면? 공통 부모가 들고 있다가 Props로 내려 주는 게 좋아요. 이걸 Lifting State Up(상태 끌어올리기)이라고 해요. 교수님은 자바 상속에서 공통 정보를 부모 클래스에 모으는 것과 비슷하다고 했어요.

깊이가 깊어지면 A가 가진 name을 I까지 C → G → I로 줄줄이 넘겨야 해요. 이걸 Prop Drilling이라고 해요. 너무 번거로워서 상태 관리 라이브러리가 나왔어요. 예전엔 Recoil, 지금은 Zustand(가볍고 쉬움)를 많이 쓰고, Redux도 많이 써요. 기말 프로젝트에 Zustand를 쓰면 "공부 좀 했네" 소리 듣는대요.

Controlled Component — 폼 입력도 State로

input을 State와 연결const [name, setName] = useState("");

<input
  value={name}                               // 입력칸 값 = State
  onChange={(e) => setName(e.target.value)}  // 칠 때마다 State 갱신 → 리렌더링
/>

한 글자 칠 때마다 onChange → setName → 리렌더링 → value에 반영이 반복돼요. 값을 브라우저가 아니라 React가 관리하니까, 제출 전에 프론트에서 Validation(유효성 검사)을 하기 쉬워요.

구분PropsState
위치Parent → Child 전달Component 내부
변경자식이 직접 변경하지 않음Setter로 변경
목적데이터 전달동적 상태 관리
시험엔 이렇게

여러 컴포넌트가 같은 데이터를 공유하면 State를 공통 Parent로 올리고(Lifting State Up) Props로 전달하며, Child의 이벤트는 Callback Props로 Parent에 전달한다. Controlled Component는 input의 value를 State에 연결하고 onChange에서 Setter로 갱신하는 방식이다. Props는 자식이 직접 변경하지 않고, State는 Setter로 변경한다.

외우는 법: 같이 쓰면 위로 올려라 / value는 State, onChange는 setter
바로 확인
형제 컴포넌트 SearchBox와 ResultList가 같은 검색어를 써야 한다. State는 어디에?
Lifting State Up. 따로 들면 동기화가 깨지고, 일반 변수는 리렌더링이 안 돼요.

컴포넌트에도 태어나고 사라지는 순간이 있다

Lifecycle · Mount · Update · Unmount · Side Effect · useEffect 소개

수업 끝에 다음 시간 예고로 본 부분이에요. 컴포넌트의 일생은 세 단계뿐이에요. 교수님이 "Unity 라이프사이클은 엄청 복잡한데 얘는 되게 심플하다"고 했죠.

단계언제보통 하는 일
Mount처음 화면(DOM)에 추가될 때 (객체의 new)API 요청, 이벤트 리스너 등록
UpdateProps / State가 바뀌어 리렌더링될 때특정 State 변화 감지
Unmount화면에서 제거될 때 (객체의 delete)타이머 · 이벤트 리스너 정리

API 요청 · 타이머 · 이벤트 리스너는 렌더링과 별개의 작업이에요. 이렇게 렌더링 자체와 직접 관계없는 외부 작업을 Side Effect라고 하고, React에선 useEffect로 관리해요. 렌더링이 끝난 뒤에 실행돼요. 잘 보면 4주차의 Web API(fetch, setInterval, addEventListener, localStorage, document.title)들이죠. 자세한 건 10/8에.

교수
React 코드 깊게 가서 보면 useEffect 떡칠돼 있고 useState 엄청 많이 나와요. 그냥 그 두 개로 이루어져 있다고 봐도 될 것 같아요.10/6 강의 중 (말을 조금 다듬음)
시험엔 이렇게

Component Lifecycle은 Mount → Update → Unmount. Side Effect는 렌더링과 직접 관계없는 외부 작업(Network 요청, Timer, Event Listener 등)이며 useEffect로 Render 이후에 처리한다.

외우는 법: 태어나고(Mount) · 변하고(Update) · 사라진다(Unmount)

① State 변수는 조용, State는 신호

  • State = UI를 결정하는 변경 가능한 데이터 · 일반 변수 ✗(감지 안 됨)
  • useState → [값, Setter] · count = count + 1 ✗

② Re-render Render 계산 · Commit 반영

  • Setter → 컴포넌트 함수 재실행 → 새 JSX → 비교 → 필요한 DOM만
  • Render(계산 · 비교) → Commit(DOM 반영) → Layout · Paint

③ Snapshot ★ 실행 결과사진이면 2, 릴레이면 4

  • 한 렌더 안 State = 고정(Snapshot) · set 직후 log → 이전 값
  • count 1, setCount(count+1)×3 → 2 / setCount(prev => prev+1)×3 → 4 (Functional Update)

④ 객체 · 배열 State ★ 면접펼쳐서 새로

  • setUser({ ...user, age: 21 }) · setItems([...items, x]) = Immutable Update
  • Spread = 얕은 복사 · 중첩은 계층마다 · user === newUser → false
  • Derived State: total = price * quantity (State ✗)

⑤ State 위치 · 폼 같이 쓰면 위로

  • Lifting State Up → Props ↓ · Callback Props ↑ · Prop Drilling → Zustand · Redux
  • Controlled Component: value={name} · onChange → setName
  • Props = 직접 변경 ✗ / State = Setter로 변경

⑥ Lifecycle 태어나고 · 변하고 · 사라진다

  • Mount → Update → Unmount · Side Effect → useEffect(Render 이후)

빈칸 채우기 눌러서 정답 확인

일반 변수는 값이 바뀌어도 React가 감지하지 못해 화면이 바뀌지 않는다. State는 반드시 Setter로 변경한다. Re-render는 컴포넌트 함수가 다시 실행되는 과정이다. State는 렌더링 시점의 Snapshot이라 이전 값에 의존하는 연속 업데이트는 Functional Update를 쓴다. 객체 State는 Spread Operator로 복사해 바꾸며 이를 Immutable Update라 한다. 여러 컴포넌트가 State를 공유하면 Lifting State Up을 고려한다.

플래시카드 알면 →, 모르면 ←

키보드: Space 뒤집기 · → 알아요 · ← 모르겠어요
State가 필요한 이유는?
일반 변수는 값이 바뀌어도 React가 감지 못 해 리렌더링이 안 된다. State 변경은 UI를 다시 계산하라는 신호.
Re-render란?
컴포넌트 함수가 다시 실행되어 새 JSX를 계산하는 과정. 실제 DOM 전체를 다시 만드는 건 아님.
Render 단계와 Commit 단계는?
Render: 컴포넌트 실행 → 새 UI 계산 → 이전과 비교. Commit: 필요한 DOM 변경을 실제 브라우저에 반영(이후 Layout · Paint).
State == Snapshot의 뜻은?
한 렌더 안에서 State는 고정값. Setter를 불러도 현재 코드의 값은 즉시 안 바뀌고 다음 렌더에서 새 값.
count 1에서 setCount(count+1)을 3번 → 결과와 이유는?
2. 세 호출 모두 같은 스냅샷 count(1)를 참조해서 모두 "2로" 요청.
Functional Update란?
setCount(prev => prev + 1)처럼 Setter에 함수를 넘김. prev는 이전 업데이트 결과 → 연속 업데이트가 순서대로 적용.
Object State를 바꾸는 올바른 방법은?
직접 속성 수정 ✗. setUser({ ...user, age: 21 })처럼 Spread로 새 객체를 만들어 교체(Immutable Update).
Spread Operator의 복사 방식과 주의점은?
얕은 복사. 새 객체를 만들지만 한 단계만 복사하므로 중첩 State는 바뀌는 계층마다 복사해야 한다.
Immutability가 React에 유리한 이유는?
이전 값과 새 값이 명확히 구분되어 변경 추적이 쉽고 렌더링이 예측 가능해진다.
Derived State란?
다른 State로 계산 가능한 값(total = price * quantity)은 State로 만들지 않고 계산해서 쓴다. 중복 저장 → 동기화 문제 방지.
Lifting State Up이란?
여러 컴포넌트가 공유하는 State를 공통 Parent로 올려 Props로 전달. Child 이벤트는 Callback Props로 올림.
Controlled Component란?
input의 value를 State에 연결하고 onChange에서 Setter로 갱신. React가 입력값을 관리 → Validation 쉬움.

    퀴즈 실행 결과 문제 위주

    Q1count가 0일 때 console.log(count); setCount(count + 1); console.log(count);의 두 출력은?

    State는 스냅샷. 같은 렌더 안에서 count는 계속 0.

    Q2count가 1일 때 setCount(prev => prev + 1)을 3번 호출하면 다음 렌더의 count는?

    prev는 이전 업데이트 결과 → 2 → 3 → 4.

    Q3count가 1일 때 setCount(count + 1)을 3번 호출하면 다음 렌더의 count는?

    셋 다 스냅샷 count(1)를 참조 → 셋 다 "2로". 교수님이 강의실에서 낸 문제.

    Q4user State가 {name:"Kim", age:20}일 때 나이를 21로 올바르게 바꾸는 코드는?

    펼쳐서 새 객체 + age만 덮어쓰기. 4번은 user가 숫자 21이 돼 버려요.

    Q5items State에 새 항목을 추가하는 올바른 코드는?

    기존 배열을 고치지 않고 새 배열로 교체(Immutable).

    Q6price · quantity가 State일 때 total을 다루는 가장 적절한 방법은?

    Derived State. 계산 가능한 값은 State로 중복 저장하지 않아요.

    Q7Props와 State에 대한 설명으로 옳지 않은 것은?

    Props는 자식이 직접 변경하지 않는 게 원칙. 부모에 알리려면 Callback Props.

    Q8<input value={name} onChange={(e) => setName(e.target.value)} />에서 사용자가 "ab"를 입력했다. 일어나는 일로 옳은 것은?

    Controlled Component. 입력할 때마다 리렌더링이 계속 일어나요.

    내 말로 설명하기 면접 대비

    "React에서 객체를 State로 넣고 값을 바꿀 때 어떻게 하는지, 왜 그렇게 하는지 설명해 보세요." (교수님 예시 면접 질문)

    객체 State는 user.age = 21처럼 직접 속성을 고치지 않고, Spread Operator로 기존 값을 펼쳐 복사한 새 객체를 만들어 Setter로 교체해요. 예: setUser({ ...user, age: 21 }). 이걸 Immutable Update라고 해요. 이렇게 하면 이전 객체와 새 객체의 주소가 달라져서 이전 값과 새 값이 명확히 구분되고, React가 변경을 추적하고 예측 가능하게 렌더링하기 쉬워요. 직접 고치면 어디서 바뀌었는지 추적하기도 어려워요. 단, Spread는 얕은 복사라 한 단계만 복사하므로, 객체 안에 객체가 있는 중첩 State는 바뀌는 안쪽 객체까지 각각 펼쳐서 복사해야 해요.
    더 알아두면 좋은 것 시험 비중 낮음

    Hook이라는 이름

    교수님 설명으로는 "무언가 끝났을 때 돌려받는 것". setter로 업데이트하면 React한테 "얘 바뀌었어"라는 신호를 날려 준다는 의미로 이해하면 편하대요. use○○ 훅은 "무언가 끝나면 무언가를 하는 애".
