Effect는 언제 실행될까? 두 번째 칸이 정한다

useEffect 기본 · Dependency Array 3가지 · StrictMode

지난 시간 끝에 본 useEffect는 렌더링이 끝난 뒤 Side Effect를 실행하는 Hook이에요. 렌더링 자체가 아니라 렌더링 후 외부 시스템과 동기화하는 작업(API 호출, 타이머, 이벤트 리스너, document.title 변경)을 맡아요. 그래서 Effect 안에서 JSX를 return하지 않아요.

원형useEffect(() => {
  // 할 일
}, dependencies);   // ← 이 두 번째 인자가 "언제"를 정한다
두 번째 인자언제 실행주로 쓰는 곳
없음매 Render 이후 (Mount + 모든 Re-render)거의 안 씀. 불필요한 반복 → 성능 저하
[ ] 빈 배열Mount 시 한 번초기 데이터 요청, 이벤트 리스너 등록
[value]Mount 후 한 번 + value가 바뀔 때마다특정 State 변화에 반응

[value]를 "업데이트 때만"이라고 착각하기 쉬운데, Mount 직후에도 한 번 실행돼요. 그리고 State가 10개 있어도 배열에 넣은 값이 같으면 나머지 9개가 아무리 바뀌어도 재실행 안 돼요.

여러 개를 넣으면?useEffect(() => {
  console.log("values are changed");
}, [count, name]);   // count 또는 name 중 하나라도 바뀌면 실행 (OR 조건)

Effect 안에서 쓰는 바깥 값을 배열에서 빠뜨리면 오래된 값을 참조하는 문제가 생겨요. 교수님 말로 useEffect 짤 때 제일 고민해야 하는 건 "Dependency가 뭐냐" 이거 하나예요.

헷갈림개발 중 콘솔에 Mounted → Unmounted → Mounted가 찍혔다. 버그다
정답npm run dev(개발 모드)의 StrictMode가 일부러 한 번 더 돌려 본 것. 빌드하면 안 뜬다. 개념상 Lifecycle과 구분해서 이해
시험엔 이렇게

useEffect는 Render 이후 Side Effect를 실행하는 Hook이며, Dependency Array에 따라 실행 시점이 정해진다. 없음 → 매 Render 이후, [] → Mount 시 1회, [value] → Mount 후 + value 변경 시. 여러 값이면 하나라도 바뀌면 실행된다.

외우는 법: 없으면 매번 · 비면 처음만 · 넣으면 바뀔 때
바로 확인
useEffect(() => console.log("hi"), [count]); — Mount 후 name State만 3번 바뀌었다. "hi"는 총 몇 번?
Mount 직후 1번. 그 뒤 name만 바뀌고 count는 그대로라 재실행 없음.

컴포넌트는 사라졌는데 setInterval은 혼자 계속 돈다

Cleanup Function · clearInterval · Timer with useEffect

Effect는 비동기적으로 뭔가를 돌리는 경우가 많아요(타이머, 이벤트 리스너, 구독). 그런데 컴포넌트가 없어졌는데도 그게 브라우저에 남아서 돌면 안 되잖아요. 그래서 Effect에서 함수를 return하면, 그게 정리 담당 Cleanup Function이 돼요.

Timer with useEffectuseEffect(() => {
  const timer = setInterval(() => {
    setSeconds(prev => prev + 1);   // 1초마다 1 증가 → 리렌더링
  }, 1000);

  return () => {
    clearInterval(timer);   // Cleanup: 타이머 정리
  };
}, []);   // Mount 때 한 번 등록
  1. Mount → 타이머 등록 (setInterval은 Web API! 콜백은 태스크 큐로)
  2. 1초마다 콜백이 setSeconds → State 변경 → 리렌더링
  3. 리렌더링돼도 타이머는 새로 안 생기고 기존 것이 계속 유지 ([]라서 Effect 재실행 없음)
  4. Unmount → Cleanup 실행 → clearInterval로 타이머 해제
교수님 비유 — Cleanup은 객체지향의 소멸자예요. Mount가 new, Unmount가 delete라면, 리소스를 잡아먹는 작업이 있을 땐 소멸자를 꼭 써 줘야 하죠.

Cleanup은 Unmount 때만이 아니라, Effect가 다시 실행되기 전에도 이전 Cleanup이 먼저 돌아요. 그래서 리소스 누수와 중복 실행을 막아요.

여기서 prev => prev + 1을 쓴 이유도 중요해요. Effect가 []로 한 번만 만들어지니까, 안에서 seconds + 1을 쓰면 처음 만들어질 때의 seconds(0)에 묶여서 0 → 1 → 1 → 1…로 멈춰요. prev는 React가 주는 최신 값이라 정확히 올라가요. (지난 시간의 스냅샷 개념!)

시험엔 이렇게

useEffect는 Cleanup Function을 반환할 수 있으며, Cleanup은 Unmount 시와 Effect 재실행 전에 실행되어 Timer · Event Listener · Subscription을 정리한다(리소스 누수 · 중복 실행 방지). 타이머는 setInterval로 등록하고 Cleanup에서 clearInterval로 해제한다.

외우는 법: return = 소멸자 / 켰으면(setInterval) 끈다(clearInterval)
바로 확인
Cleanup 없이 [isRunning]에 따라 setInterval을 켜는 타이머에서 Start / Pause를 여러 번 반복하면?
이전 interval을 안 지우니 계속 쌓여요. 그래서 Cleanup이 중복 실행을 막아요.

데이터는 언제 불러오고, Effect를 쓰면 안 되는 때는 언제일까?

Fetch with useEffect · Avoid Unnecessary Effects · Infinite Effect Loop
Fetch with useEffectuseEffect(() => {
  async function loadData() {
    const response = await fetch("/api/users");   // 응답 올 때까지 대기
    const data = await response.json();          // JSON 변환 끝날 때까지 대기
    setUsers(data);                                 // State에 저장 → 리렌더링
  }
  loadData();
}, []);   // Mount 이후 한 번

4주차 async / await가 그대로 나와요. async 함수는 Promise를 반환하고, await는 비동기를 동기처럼 기다리게 해 주죠. 데이터가 JSON(객체)이니 users는 객체 · 배열을 담는 State겠구나 하고 읽을 수 있어요. Fetch 자체는 렌더링 바깥에서 도는 Side Effect라, []로 Mount 때 딱 한 번 부르면 돼요. 보통 Loading · Error State도 같이 관리해요.

이런 Effect는 쓰지 마세요

✗ 불필요한 EffectuseEffect(() => {
  setTotal(price * quantity);
}, [price, quantity]);
// ○ 그냥 렌더 중에 계산: const total = price * quantity;

지난 시간 Derived State처럼, State로 계산할 수 있는 값은 Effect로 다시 저장할 필요가 없어요. 오히려 리렌더링이 한 번 더 생겨요. 교수님 말로 "오버엔지니어링". Effect는 외부 시스템과 동기화가 필요할 때만.

✗ 무한 루프useEffect(() => {
  setCount(count + 1);
}, [count]);
// count 변경 → Effect 실행 → setCount → count 변경 → Effect 실행 → … 끝없이
시험엔 이렇게

API 요청은 대표적인 Side Effect로 보통 useEffect(…, [])에서 Mount 이후 실행하고 응답을 State에 저장한다. 렌더 중 계산 가능한 값을 Effect로 저장하지 않는다. Effect 안에서 자신의 Dependency를 변경하면 무한 루프가 발생한다.

외우는 법: 불러오기는 [] · 계산은 그냥 · 내 꼬리 물면 무한루프
바로 확인
useEffect(() => { setCount(count + 1); }, [count]);를 실행하면?
count가 바뀌면 Effect, Effect가 count를 또 바꾸니 무한 반복.

Start · Pause · Reset · 숨기기까지, 타이머를 5단계로 쌓아 보자

Timer 실습 Step 1~5 · [isRunning] · Reset은 Event Handler · 조건부 렌더링 = Mount/Unmount
Step추가한 것핵심 포인트
1seconds State (초깃값 0)로 화면 표시화면에 보여 줄 값이라 State
2isRunning State + handleStart / handlePause아직 setInterval 없이 Running / Paused 글자만 바뀜
3useEffect + setInterval + Cleanup, [isRunning]isRunning이 true일 때만 1초마다 prev => prev + 1
4Reset: setSeconds(0)Effect가 아니라 Event Handler에서
5App에 showTimer State + 숨기기 버튼숨기면 Unmount, 보이면 Mount
Step 3 — Timer.jsx의 타이머 EffectuseEffect(() => {
  if (!isRunning) return;          // Paused면 타이머 안 만들고 끝
  const id = setInterval(() => {
    setSeconds(prev => prev + 1);
  }, 1000);
  return () => clearInterval(id);   // Pause(isRunning 변경) 또는 Unmount 때 정리
}, [isRunning]);

왜 [isRunning]? — Start / Pause로 isRunning이 바뀔 때만 타이머를 새로 켜거나 꺼야 하니까요. []면 처음 한 번뿐이라 Start / Pause가 안 먹히고, 배열을 빼면 매초 리렌더링마다 껐다 켰다 낭비예요.

seconds는 왜 안 넣나? — prev 덕분에 Effect 안에서 seconds를 직접 안 쓰거든요.

Reset은 왜 Effect에 안 넣나? — "사용자가 버튼을 눌렀다"는 사건 때문에 한 번 일어나는 일이라, 그 사건을 받는 Event Handler가 제자리예요. Reset은 seconds(데이터)만 0으로 바꾸고 isRunning(스위치)은 안 건드리니 Start / Pause 상태가 유지돼요.

Step 5 — App.jsxconst [showTimer, setShowTimer] = useState(true);
const handleToggle = () => setShowTimer(prev => !prev);   // 토글 단골 패턴

<button onClick={handleToggle}>{showTimer ? "타이머 숨기기" : "타이머 표시"}</button>
{showTimer && <Timer />}   // true일 때만 그림 → 사라지면 Unmount

조건 ? A : B는 if-else 한 줄 버전(삼항 연산자), A && B는 A가 true일 때만 B를 그려요. 숨기면 Timer가 통째로 사라져서 Cleanup이 돌고("Timer Unmounted"), 다시 보이면 새로 Mount돼서 seconds도 0부터 다시 시작해요.

추가 미션: (1) Lap 기록(현재 seconds를 배열 State에 [...prev, seconds]로 추가), (2) 목표 시간 도달 시 문구 + 자동 Pause, (3) 정수 → 실수(0.1초). 끝난 사람은 designmd.ai의 디자인 시스템 마크다운을 AI에게 줘서 디자인해 보라고 했어요.

시험엔 이렇게

타이머 Effect는 isRunning이 true일 때만 setInterval을 등록하고 Cleanup에서 clearInterval하며 Dependency Array는 [isRunning]이다. 사용자 클릭으로 한 번 일어나는 Reset은 Event Handler에서 처리한다. 조건부 렌더링으로 컴포넌트를 숨기면 Unmount(Cleanup 실행), 다시 보이면 Mount된다.

외우는 법: 스위치는 isRunning · 클릭 일은 핸들러 · 숨기면 Unmount

타이머가 7초에서 Running 중일 때 Reset을 누르면?
Reset은 seconds만 0으로. isRunning은 그대로 true라 0부터 계속 올라가요(prev 기준이라 0 → 1 → 2).

Event Handler vs Effect도 헷갈리기 쉬워요. Event Handler는 "클릭할 때 / 엔터 칠 때" 무언가 일어나게 하는 것, Effect는 "렌더링 뒤에" 무언가 일어나게 하는 것이에요. 설명은 비슷해 보여도 역할이 달라요.

전체 Lifecycle Flow

  1. Mount: Render → Commit → (Mount 조건) Effect 실행
  2. Update: State / Props 변경 → Render → Commit → 이전 Cleanup → Effect 재실행 → 반복
  3. Unmount: 컴포넌트 제거 → Cleanup
교수
React는 사실 이 개념이 거의 끝이에요. useEffect랑 useState 잘 쓰고, 컴포넌트 어떻게 쪼개고, 리렌더링 언제 일어나는지, 그것만 잘하면 거의 끝이거든요.10/8 강의 중 (말을 조금 다듬음)

다음 주(7주차)엔 React 아키텍처, 그다음이 중간고사. 9주차부터 TypeScript(약 3주) → Next.js(2~3주). 기말 프로젝트는 기획서 · 코드 · 보고서 · 발표라 지금부터 주제를 고민해 두래요. 커밋은 기능 단위로 잘게(롤백 대비).

시험엔 이렇게

useState는 UI 상태를 관리하며 Event 등으로 변경되면 Re-render를 일으키고, useEffect는 Render 이후 외부 시스템과 동기화하는 Side Effect를 처리한다. Event Handler는 사용자 이벤트에 반응하고, Effect는 렌더링 이후에 실행된다. Effect는 가능한 한 외부 시스템과 동기화가 필요할 때만 쓴다.

빈칸 채우기 눌러서 정답 확인

useEffect는 Render 이후 Side Effect를 실행하는 Hook이다. 두 번째 인자가 없으면 매 Render 이후, 빈 배열이면 Mount 시 한 번, [count]면 count가 변경될 때 실행된다. Effect가 반환하는 Cleanup 함수는 Unmount 시 실행되며, 타이머는 clearInterval로 정리한다. 사용자 클릭으로 일어나는 Reset은 Event Handler에서 처리한다.

Effect(Side Effect)란?
렌더링 자체가 아니라 렌더링 이후 외부 시스템과 동기화하는 작업(API 호출, 타이머, 이벤트 리스너, document.title 등).
Dependency Array가 없을 때?
매 Render 이후(Mount + 모든 Re-render) 실행. 잘못 쓰면 불필요한 반복.
Dependency Array가 []일 때?
Mount 이후 한 번. 초기 데이터 요청 · 이벤트 리스너 등록. Cleanup은 Unmount 시.
[count]일 때?
Mount 후 한 번 + count가 바뀔 때마다. 다른 State가 바뀌어도 count가 같으면 재실행 안 함.
[count, name]일 때?
둘 중 하나라도 바뀌면 실행(OR 조건).
Cleanup Function의 실행 시점과 역할은?
Unmount 시 + Effect 재실행 전. Timer · Event Listener · Subscription 정리 → 누수 · 중복 실행 방지.
Fetch는 useEffect에서 어떻게?
async 함수 안에서 await fetch → await json → setState, Dependency []로 Mount 이후 한 번.
Infinite Effect Loop가 생기는 경우는?
useEffect(() => setCount(count + 1), [count]) — Effect가 자기 Dependency를 바꿔 끝없이 반복.
타이머 Effect의 Dependency가 [isRunning]인 이유는?
Start / Pause로 isRunning이 바뀔 때만 타이머를 켜고 꺼야 하므로. seconds는 prev로 써서 넣을 필요 없음.
Reset을 Effect가 아닌 Event Handler에 두는 이유는?
사용자 클릭이라는 사건으로 한 번 일어나는 일이라. Effect는 렌더링 결과에 맞춰 외부를 동기화하는 곳.
showTimer && <Timer />에서 showTimer가 false가 되면?
Timer가 트리에서 빠져 Unmount → Cleanup 실행. 다시 true면 새로 Mount, State도 초깃값부터.
State vs Effect 한 줄 비교는?
State: UI 상태 관리, Event로 변경 → Re-render. Effect: 외부 시스템 동기화, Render 이후 실행 → Side Effect 처리.

    퀴즈 실행 결과 문제 위주

    Q1useEffect(() => console.log("Effect")); — Mount 후 State가 2번 바뀌었다. "Effect"는 몇 번?

    배열이 없으면 매 Render 이후. Mount 1 + Re-render 2 = 3.

    Q2useEffect(() => console.log("Mounted"), []); — Mount 후 State가 5번 바뀌었다. 몇 번? (빌드 기준)

    빈 배열 → Mount 때만.

    Q3다음 코드에서 컴포넌트가 Unmount될 때 일어나는 일은? useEffect(() => { const t = setInterval(tick, 1000); return () => clearInterval(t); }, []);

    return한 함수 = Cleanup → Unmount 시 clearInterval.

    Q4[] Effect 안에서 setInterval(() => setSeconds(seconds + 1), 1000)으로 쓰면 화면 숫자는?

    Effect가 처음 만들어질 때의 seconds(0)에 묶여 계속 "0 + 1 = 1"을 요청. 그래서 prev => prev + 1을 써요.

    Q5useEffect(() => { … }, [count, name]);이 다시 실행되는 경우는?

    여러 Dependency는 OR 조건.

    Q6Timer가 Paused, seconds 4일 때 Reset을 누르면?

    Reset은 seconds만 0. isRunning(false)은 그대로.

    Q7useEffect를 쓰기에 부적절한 것은?

    렌더 중 계산 가능한 값은 Effect가 필요 없어요(추가 리렌더링 유발).

    Q8State와 Effect 비교로 옳은 것은?

    6주차 p.47 표 그대로.

    내 말로 설명하기 주관식 대비

    "Timer 컴포넌트에서 useEffect의 Dependency Array를 [isRunning]으로 하고 Cleanup을 쓰는 이유를 설명해 보세요."

    타이머는 isRunning이 true일 때만 setInterval로 1초마다 seconds를 올려야 해요. 그래서 Start / Pause로 isRunning이 바뀔 때만 Effect가 다시 실행되도록 [isRunning]을 넣어요. []로 하면 Mount 때 한 번만 실행돼 Start / Pause가 반영되지 않고, 배열을 빼면 매초 리렌더링마다 타이머를 껐다 켜서 낭비예요. seconds는 setSeconds(prev => prev + 1)로 최신 값을 받으니 넣을 필요가 없어요. Cleanup에서 clearInterval을 하는 이유는, Effect가 다시 실행되기 전(Pause 등)과 Unmount 때 이전 타이머를 정리하지 않으면 타이머가 쌓여 속도가 빨라지거나, 컴포넌트가 사라진 뒤에도 계속 돌아 리소스가 새기 때문이에요.
