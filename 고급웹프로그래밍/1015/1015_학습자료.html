코드를 전부 App.jsx 하나에 넣으면 뭐가 문제일까?

Step 1 · 장바구니 UI · 컴포넌트 분리

상품 3개(Keyboard 50,000 · Mouse 30,000 · Monitor 300,000), 상품마다 Add to Cart 버튼, 화면 아래 Cart 영역

Step 1은 이 화면을 만드는 거예요. 아직 useReducer는 안 쓰고, Cart에는 "장바구니가 비어있습니다" 문구만 띄웁니다.

교수님이 LLM에게 이 프롬프트를 넣었더니, 코드가 App.jsx 하나에 전부 들어간 채로 나왔어요. 돌아가긴 하죠. 그런데 교수님이 바로 물어봤어요. "이렇게 짜면 단점이 뭐죠?"

답은 간단해요. 코드가 너무 길어서 보기 어렵고, 하나에 다 몰려 있으니 뭘 찾아서 고치기가 어려워요. 그래서 화면을 역할별로 잘라요. 상품 한 줄을 그리는 ProductItem, 장바구니 영역을 그리는 Cart, 그리고 둘을 품고 State를 가진 App. 이렇게 나눠 둔 파일들이 보통 components 폴더에 들어가는데, 깃허브에 있는 대부분 React 프로젝트가 이 구조를 써요.

장면 2

Keyboard를 두 번 담으면 장바구니에 두 줄이 생길까?

Step 2 · cartReducer · ADD_ITEM · quantity

Step 2에서 드디어 useReducer를 붙여요. 장바구니 State는 처음에 { items: [] }, 빈 배열 하나예요. 버튼을 누르면 dispatch({ type: "ADD_ITEM", payload: product })로 "이 상품 담아 줘"라는 Action을 보내고, 실제로 items를 바꾸는 건 cartReducer가 해요.

규칙은 두 개예요. 처음 담는 상품이면 quantity 1로 추가, 이미 있는 상품이면 quantity만 1 증가. 그러니까 Keyboard를 두 번 눌러도 줄은 하나, 수량이 2가 돼요.

cartReducer.js · ADD_ITEM (실습 코드)case "ADD_ITEM": {
  const product = action.payload;   // 누른 상품 { id, name, price }
  // 이미 장바구니에 있나? id로 찾기
  const exists = state.items.find(item => item.id === product.id);
  if (exists) {
    return {
      ...state,
      items: state.items.map(item =>   // map → 새 배열
        item.id === product.id
          ? { ...item, quantity: item.quantity + 1 }  // 그 상품만 +1
          : item                                      // 나머지 그대로
      ),
    };
  }
  // 처음 담는 상품 → 복사한 새 배열 끝에 quantity 1로 추가
  return {
    ...state,
    items: [...state.items, { ...product, quantity: 1 }],
  };
}

여기서 눈여겨볼 건 push나 quantity++가 한 번도 안 나온다는 거예요. 기존 배열을 고치는 대신 map과 [...배열, 새것]으로 새 배열 · 새 객체를 만들어 돌려줘요. 6주차에 배운 것처럼 React는 "주소가 바뀌었나"로 변화를 알아채거든요. 이걸 Immutable Update(불변 업데이트)라고 해요.

시험엔 이렇게

Reducer는 현재 State와 Action을 받아 새로운 State를 반환한다. 기존 State를 직접 수정하지 않고 새 Object · Array를 만들어 반환한다(Immutable Update).

장면 3

빼기 · 삭제 · 비우기도 "고치지 않고" 바꿀 수 있을까?

Step 3 · INCREASE · DECREASE · REMOVE · CLEAR · map · filter · Spread

Step 3은 진짜 쇼핑몰 장바구니처럼 기능을 늘리는 단계예요. 교수님 말로 "조건을 좀 빡빡하게" 줬어요. 모든 변경은 dispatch로, 규칙은 전부 cartReducer 안에, map · filter · Spread로 불변 업데이트, 그리고 Event Handler에서 State를 직접 바꾸지 말 것.

Action type버튼reducer가 하는 일쓰는 도구
ADD_ITEMAdd to Cart처음이면 수량 1로 추가, 있으면 +1find · map · [...]
INCREASE_QUANTITY+그 상품만 quantity + 1map + {...item}
DECREASE_QUANTITY-quantity − 1, 단 최소 1 유지map + Math.max(1, …)
REMOVE_ITEMRemove그 상품을 빼기filter (id가 다른 것만 남김)
CLEAR_CARTClear Cart장바구니 통째로 비우기items: [ ] (새 빈 배열)
(모르는 type)State를 그대로 반환default: return state
cartReducer.js · DECREASE / REMOVE (실습 코드)case "DECREASE_QUANTITY":
  return {
    ...state,
    items: state.items.map(item =>
      item.id === action.payload        // payload = 상품 id
        // Math.max(1, …) → 1 밑으로 안 내려감
        ? { ...item, quantity: Math.max(1, item.quantity - 1) }
        : item
    ),
  };
case "REMOVE_ITEM":
  return {
    ...state,
    // 그 id만 빠진 새 배열
    items: state.items.filter(item => item.id !== action.payload),
  };

헷갈리기 쉬운 곳이 둘 있어요. 하나, 수량 1에서 - 를 누르면 상품이 사라지는 게 아니라 1 그대로예요. 빼고 싶으면 Remove를 눌러야 하죠. 둘, filter는 조건이 true인 것만 남겨요. 그래서 "지울 id와 다른 것만 남겨라"(!==)가 곧 삭제예요.

총 금액은 State에 따로 저장하지 않아요. items만 있으면 언제든 계산되니까 화면을 그릴 때마다 items.reduce((sum, item) => sum + item.price * item.quantity, 0)로 구해요. 이미 있는 State로 계산할 수 있는 값은 State로 또 만들지 않는 거예요.

시험엔 이렇게

상태 변경 규칙은 모두 Reducer 안에 두고, map() · filter() · Spread Syntax로 Immutable Update를 한다. Event Handler는 State를 직접 바꾸지 않고 dispatch()로 Action만 전달한다.

외우는 법: 바꾸기는 map, 빼기는 filter, 복사는 ...
✗ 이렇게 쓰면 틀려요state.items.push(product); return state; — 같은 배열을 고쳐서 그대로 돌려주면 React는 "안 바뀌었네" 하고 화면을 다시 안 그려요
○ 맞게 쓰기return { ...state, items: [...state.items, { ...product, quantity: 1 }] }; — 새 객체 · 새 배열
바로 확인
items가 Keyboard ×2, Mouse ×1일 때 DECREASE_QUANTITY(Mouse) → REMOVE_ITEM(Keyboard) 순서로 dispatch했다. 결과는?
Mouse는 이미 1이라 Math.max(1, 0) = 1 그대로. 그다음 Keyboard를 filter로 빼면 Mouse ×1만 남아요. 30,000 × 1 = 30,000원.

장면 4

State는 App에 있는데, + 버튼은 Cart 안에 있다면?

Lifting State Up · Props로 내려받기 · 콜백 Props로 dispatch

컴포넌트를 나누고 나면 질문이 하나 생겨요. 장바구니 State(cart)와 dispatch는 App에 있는데, 버튼은 아래 Cart와 ProductItem에 있잖아요. 교수님이 수업 중에 직접 물어봤어요. "나머지 컴포넌트는 상태를 뭘로 내려받아요?" 답은 Props.

장바구니 목록은 ProductItem과 Cart가 같이 쓰는 데이터라서 공통 부모인 App으로 올려 둬요(Lifting State Up). 그리고

  • 데이터는 아래로 — App이 items={cart.items}를 Props로 Cart에 내려 줘요.
  • 이벤트는 위로 — App이 onRemove={handleRemove}처럼 함수를 Props로 내려 주고, Cart는 버튼이 눌리면 onRemove(item.id)를 부르기만 해요. 그러면 App의 핸들러가 dispatch를 실행해요.
교수
리프팅 업 가지고 상태를 공통으로 쓰는 애는 항상 위로 올렸잖아요. 앱에다가 상태를 주고 나머지 컴포넌트는 프롭스로 내려받아서 쓸 거야. 이벤트 처리가 되면 디스패치로 다시 위로 타고 올라와서 처리하게. 콜백을 프롭스로 전달하겠다.10/15 강의 중 (말을 조금 다듬음)
App.jsx · Cart.jsx (실습 코드 줄임)function App() {
  const [cart, dispatch] = useReducer(cartReducer, { items: [] });
  function handleRemove(id) {
    // 직접 안 바꾸고 Action만 보냄
    dispatch({ type: "REMOVE_ITEM", payload: id });
  }
  // 데이터 + 콜백을 Props로 내려 줌
  return <Cart items={cart.items} onRemove={handleRemove} />;
}
function Cart({ items, onRemove }) {
  return items.map(item =>
    // 자식은 콜백을 호출만 한다
    <button key={item.id} onClick={() => onRemove(item.id)}>Remove</button>
  );
}

ProductItem에 onClick={() => onAdd(product)}처럼 화살표 함수로 감싼 이유도 같이 알아 두세요. onClick={onAdd(product)}라고 쓰면 클릭할 때가 아니라 화면을 그리는 순간 바로 실행돼 버려요. "클릭하면 이 상품을 넘기며 실행해 줘"라는 뜻으로 함수를 하나 감싸서 넘기는 거예요.

시험엔 이렇게

공유 State는 공통 부모로 올리고(Lifting State Up) 자식에게 Props로 내려 준다. 자식의 이벤트는 콜백 Props로 부모에게 올라가 dispatch(action)로 처리된다(One-Way Data Flow).

외우는 법: 데이터는 Props로 내려가고, 이벤트는 콜백으로 올라온다
바로 확인
Cart의 Remove 버튼을 눌렀을 때 일어나는 순서로 맞는 것은?
자식은 콜백만 부르고, 실제 변경은 위에서 dispatch → Reducer가 해요. 7주차 자료 p.16 흐름 그대로예요: User Event → dispatch(action) → Reducer → New State → Re-render.

왜 이 예제는 useState가 아니라 useReducer였을까?

Step 4 · LLM과 대화하기 · Q1~Q4

Step 4는 코드가 아니라 질문 4개예요. 먼저 내 생각을 적고 LLM에게 물어서 비교해 보라고 했죠. 교수님은 "4개 중 3개 정도는 맞춰야 리듀서를 잘 이해했다고 할 수 있다"고 하면서 직접 답을 풀어 줬어요. 개념 주관식으로 그대로 나오기 좋은 질문들이라 하나씩 정리할게요.

질문교수님 답 (수업 중)
Q1 왜 useState보다 useReducer?Action이 모든 상품에 똑같다. 상품마다 setter 함수를 따로 만들면 엄청 복잡해지는데, Reducer 하나로 묶으면 코드가 가벼워진다. 최상단의 Reducer 하나만 관리하면 얘만 고쳐도 전부 바뀐다.
Q2 dispatch()의 역할은?Action을 Reducer에 전달해 실행해 주는 것. ("되게 간단한 답")
Q3 Reducer가 State를 직접 수정하면 안 되는 이유?불변(Immutable) 업데이트로 안전하게 상태를 바꾸기 위해서. 새 객체를 돌려줘야 React가 변경을 알아챈다.
Q4 Action Type을 쓰는 이유?무슨 변경인지 의도를 명확하게 표현해 코드를 이해 · 관리하기 쉽게. type이 분명하면 검색해서 다 찾아낼 수 있다.
교수
상품 1번부터 3번까지 액션이 다 동일하죠? 스테이트 하나당 이 함수들을 다 하나씩 구현해 준다고 생각하면 엄청 복잡해집니다. 리듀서로 묶어서 처리하기 되게 좋아. 얘만 수정하면 모든 걸 바꿀 수 있어요. 이게 좀 큰 장점이에요.10/15 강의 중 (말을 조금 다듬음)

7주차 자료 p.18 표와 같이 보면 깔끔해요. Toggle · Input · Counter처럼 단순하면 useState, Form · Cart · Todo처럼 변경 규칙이 많으면 useReducer. 장바구니는 표에 이름까지 적혀 있는 대표 예시예요.

시험엔 이렇게

State 변경 규칙을 Reducer 한곳에 모을 수 있어 코드의 일관성과 유지보수성이 향상된다. 단순한 상태는 useState, 변경 규칙이 많고 복잡한 상태는 useReducer가 적합하다.

외우는 법: 간단하면 useState, 규칙 많으면 useReducer (Cart · Form · Todo)

빈칸 채우기 눌러서 정답 확인

장바구니의 초기 State는 { items: [] }이다. 버튼을 누르면 Event Handler는 State를 직접 바꾸지 않고 dispatch()로 Action을 보낸다. ADD_ITEM에서 처음 담는 상품은 quantity 1로 추가하고, 이미 있는 상품은 map()으로 quantity를 1 늘린다. REMOVE_ITEM은 filter()로 해당 id만 뺀 새 배열을 만든다. DECREASE_QUANTITY는 최소 수량 1을 유지한다. 이렇게 기존 State를 고치지 않고 새 Object · Array를 반환하는 것을 Immutable Update라고 한다. 공유 State는 공통 부모로 올리고(Lifting State Up) 자식에게 Props로 내려 준다.

중간고사 문제 구성은?
18문제 = 객관식 8 + 주관식 10. 주관식은 코드 해석 · 실행 결과 쓰기 · 개념. 손코딩 없음.
App.jsx 하나에 다 짜면 단점은?
코드가 길어 보기 어렵고, 고칠 곳을 찾기 어렵다. 컴포넌트로 나눠야 재사용성 · 가독성 · 유지보수성이 좋아진다.
ADD_ITEM 규칙 두 가지는?
처음 담는 상품이면 quantity 1로 추가, 이미 있는 상품이면 quantity + 1.
수량 1에서 DECREASE_QUANTITY를 하면?
1 그대로 (최소 수량 1 유지). 빼려면 REMOVE_ITEM.
REMOVE_ITEM은 어떻게 구현하나?
filter로 id가 다른 상품만 남긴 새 배열을 만든다. items.filter(item => item.id !== action.payload)
Reducer에 모르는 type이 오면?
default에서 state를 그대로 반환 → 화면 변화 없음.
Q1. 왜 useState보다 useReducer?
모든 상품에 같은 Action이 반복된다. 변경 규칙을 Reducer 하나에 모으면 코드가 가볍고, 그것만 고치면 전체가 바뀐다.
Q2. dispatch()의 역할은?
Action을 Reducer에 전달해 State 변경을 요청(실행)하는 것.
Q3. Reducer가 State를 직접 수정하면 안 되는 이유는?
Immutable Update로 안전하게 바꾸기 위해. 새 객체를 반환해야 React가 변경을 알아채고 리렌더링한다.
Q4. Action Type을 쓰는 이유는?
어떤 변경인지 의도를 명확히 해서 코드를 이해 · 관리하기 쉽게. 검색으로 찾기도 쉽다.
Cart의 버튼이 App의 State를 바꾸는 방법은?
App이 내려 준 콜백 Props(onRemove 등)를 호출 → App의 핸들러가 dispatch.

    퀴즈 다 풀고 채점하기 · 실행 결과 위주

    Q1빈 장바구니에서 Keyboard(50,000) → Mouse(30,000) → Keyboard 순서로 ADD_ITEM을 dispatch했다. 총 금액은?

    Keyboard ×2 + Mouse ×1 = 100,000 + 30,000 = 130,000원. 두 번째 Keyboard는 새 줄이 아니라 quantity가 2가 돼요.

    Q2Q1 상태에서 DECREASE_QUANTITY(Keyboard)를 두 번 dispatch했다. items는?

    2 → 1, 그다음은 Math.max(1, 0) = 1. 최소 수량 1이라 사라지지 않아요. 총 80,000원.

    Q3items.filter(item => item.id !== 2)의 결과로 맞는 것은? (items = Keyboard(id 1), Mouse(id 2), Monitor(id 3))

    filter는 조건이 true인 것만 남겨요. "id가 2가 아닌 것"만 남으니 Mouse가 빠져요. REMOVE_ITEM이 이 모양이에요.

    Q4Reducer 안에 state.items.push(product); return state;라고 썼다. 무슨 일이 생길까?

    기존 State를 직접 고치고 같은 참조를 반환하면 React는 바뀐 게 없다고 봐요. 그래서 새 Object · Array를 만들어 반환해야 해요(Immutable Update).

    Q5Mouse ×1만 있는 장바구니에서 INCREASE_QUANTITY(Mouse)를 두 번 dispatch했다. 총 금액은?

    1 → 2 → 3. 30,000 × 3 = 90,000원.

    Q6Monitor를 담은 뒤 CLEAR_CART, 이어서 Mouse를 ADD_ITEM 했다. items는?

    CLEAR_CART가 items를 새 빈 배열로 바꾼 뒤 Mouse가 처음 담기니 quantity 1이에요.

    Q7교수님이 말한 "이 예제에서 useState보다 useReducer가 좋은 이유"에 가장 가까운 것은?

    같은 Action을 Reducer 하나로 묶어 처리하고, 그 하나만 고치면 전체가 바뀌는 게 장점이에요. 속도나 Props와는 상관없어요.

    내 말로 설명하기 친구한테 말하듯이

    장바구니에서 Remove 버튼을 누르면 화면이 바뀌기까지 무슨 일이 일어나는지, Props · dispatch · Reducer · filter를 넣어서 설명해 보세요.

    장바구니 State와 dispatch는 공통 부모인 App에 있고, Cart는 items와 onRemove 같은 콜백을 Props로 받아요. Remove를 누르면 Cart는 onRemove(상품 id)를 부르기만 하고, App의 핸들러가 dispatch({ type: "REMOVE_ITEM", payload: id })로 Action을 보내요. cartReducer는 filter로 그 id가 아닌 상품만 남긴 새 배열을 담은 새 State를 반환하고, React가 바뀐 State로 다시 렌더링해서 그 상품이 화면에서 사라져요.
