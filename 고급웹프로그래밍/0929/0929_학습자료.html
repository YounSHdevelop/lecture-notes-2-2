React 소개 · 바닐라 JS의 Pain point · Imperative vs Declarative

React는 UI를 만드는 JavaScript 라이브러리예요. Facebook(지금의 Meta)이 2013년에 공개했고, 2015년 ES6를 만나 2016~17년쯤 주류가 됐어요. 화면을 컴포넌트로 나누고, 데이터가 바뀌면 UI를 자동으로 다시 그려 줘요. 페이지 하나에서 화면이 바뀌는 SPA(Single Page Application) 개발에 널리 쓰여요.

교수
프론트엔드 개발자로 취업하고 싶으면 React 없으면 개발을 못 합니다. 프론트엔드를 꿈꾼다면 무조건 React. 우리나라뿐 아니라 해외도 똑같아요.9/29 강의 중 (말을 조금 다듬음)

바닐라 JS는 뭐가 힘들었나

바닐라 JS(순수 JS)로 짜면 상태가 바뀔 때마다 내가 직접 DOM을 찾아가서 바꿔야 해요. 값이 바뀌면 querySelector로 요소 찾고, textContent 바꾸고, classList 바꾸고… 화면이 커질수록 DOM 바꾸는 코드가 늘고, 데이터와 화면을 맞추는 게 복잡해져요. 이게 Pain point예요.

명령형 (Imperative) — 바닐라 JS: "어떻게 바꿀지" 하나하나 명령title.textContent = "Hello";
title.classList.add("active");

선언형 (Declarative) — React: "지금 상태면 화면이 이래야 해"<h1 className={active ? "active" : ""}>{title}</h1>

선언형에선 나는 상태(active, title)만 바꾸고, DOM을 실제로 고치는 건 React가 해요.

시험엔 이렇게

명령형 UI는 DOM을 어떻게 바꿀지 직접 명령하는 방식(바닐라 JS)이고, 선언형 UI는 현재 상태에서 UI가 무엇이어야 하는지 선언하면 React가 DOM 변경을 처리하는 방식이다.

외우는 법: 명령형 = 어떻게 · 선언형 = 무엇

붕어빵 틀 하나로 팥 붕어빵, 슈크림 붕어빵을 다 찍는다

Component · Element · JSX · Function Component

Component는 화면을 이루는 독립적인 UI 단위예요. 버튼, 카드, 헤더 같은 걸 하나씩 컴포넌트로 만들어 두고, 필요한 곳에서 불러 써요. 똑같은 게 여러 번 나오면 컴포넌트 하나만 고치면 되니까 재사용성과 유지보수성이 확 올라가요. HTML로 깡으로 짜면 반복이 어려워서 코드가 점점 길어지는데, React는 그걸 해소해요.

교수님 비유 — 붕어빵
컴포넌트 = 붕어빵 틀. 원하는 위치에서 호출하면 찍혀 나오는 붕어빵 = Element. 어떤 사람은 팥, 어떤 사람은 슈크림을 좋아하니까, 틀은 똑같이 쓰되 안의 내용(다음 장면의 Props)만 바꿔 주자는 거예요.

JSX — JS 안에서 HTML처럼 쓰기

React는 HTML 파일을 직접 짜지 않아요. 그걸 가능하게 하는 게 JSX(JavaScript Syntax Extension)예요. HTML처럼 생겼지만 HTML이 아니라 JS 문법 확장이고, 교수님 말로 JS의 "DLC(확장팩)"예요. 빌드 과정에서 JS 코드로 바뀌어요.

JSX와 실제 변환 결과const element = <h1>Hello React</h1>;
// 빌드하면 ↓
const element = React.createElement("h1", null, "Hello React");

Function Componentfunction Welcome() {      // 이름은 대문자로 시작
  return <h1>Hello React</h1>;  // JSX를 반환
}
<Welcome />                    // 내가 만든 HTML 태그처럼 사용
시험엔 이렇게

Component는 독립적인 UI 단위로 조합 · 재사용이 가능하다. JSX는 HTML이 아닌 JavaScript Syntax Extension이며 빌드 시 React.createElement 등 JS 코드로 변환된다. Function Component는 이름을 대문자로 시작하고 JSX를 반환한다.

외우는 법: 틀 = Component · 붕어빵 = Element / JSX = JS의 DLC

JSX는 HTML이 아니에요. React.createElement 같은 JS로 변환된 뒤 실행돼요.

틀(컴포넌트)은 같아도 내용은 달라야 하잖아요. 그 내용을 부모가 자식에게 넘겨주는 데이터가 Props예요. 반면 컴포넌트가 스스로 들고 있으면서 바뀔 수 있는 값은 State예요.

count = count + 1 했는데 왜 화면 숫자가 그대로지?

useState · setState · State 변경 → 리렌더링 흐름

바뀌는 값을 만들려면 React가 주는 기능(Hook)을 써요. 그중 하나가 useState예요. 이름부터 "상태를 쓰고 싶어"죠.

useState 문법import { useState } from 'react';
const [state, setState] = useState(initialState);

state — 현재 값. 처음엔 initialState가 들어가요. 숫자 · 문자열 · 객체 뭐든 돼요.

setState — 값을 바꾸는 함수. 이걸 불러야 값이 바뀌고 자동으로 리렌더링돼요. 둘은 짝꿍이에요.

initialState — 초깃값.

그럼 그냥 count = count + 1 하면 안 되냐고요? 선언이 const라 재할당이 안 되고, 무엇보다 React는 setState를 불러야만 값이 바뀐 걸 알아요. 그래서 setCount를 써야 해요.

Counter 컴포넌트function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
// 처음 버튼엔 0 → 클릭 → 1 → 클릭 → 2

클릭 한 번에 일어나는 일

①②③④⑤⑥
User ClicksetCount()State 변경Component Re-render새 UI 계산DOM Update

너무 빨라서 우리는 못 느껴요. 핵심은 개발자는 State만 바꾸고, UI 업데이트는 React가 한다는 거예요.

시험엔 이렇게

const [state, setState] = useState(initialState). state는 현재 값, setState는 상태를 갱신하고 리렌더링을 트리거하는 함수다. 흐름: User Click → setState → State 변경 → Re-render → 새 UI 계산 → DOM Update.

useState(initialState)의 인자 = 초깃값. 처음 화면에 5가 보여요.

버튼 하나 바뀌었는데 페이지 전체를 다시 그려야 할까? (면접 단골)

Virtual DOM · flickering · 비교 · 메모리

실제 DOM은 브라우저가 들고 있는 단 하나의 객체예요. 이걸 업데이트할 때마다 화면이 깜빡깜빡할 수밖에 없는데, 이걸 flickering이라고 해요. 실제 서비스 페이지는 컴포넌트가 엄청 많은데, 하나 바뀌었다고 전체를 다시 그리면 오래 걸리고 손해가 막심하죠.

그래서 React가 낸 아이디어가 Virtual DOM이에요. DOM의 복사본을 메모리에 하나 더 들고 있는 거예요.

  1. UI 구조를 JS 객체 형태로 메모리에 들고 있어요 (Virtual DOM)
  2. State가 바뀌면 새 Virtual DOM(새 UI 결과)을 계산해요
  3. 이전 결과와 새 결과를 비교해요
  4. 필요한 실제 DOM 변경만 수행해요

조금만 교체하고도 전체 페이지가 바뀐 효과를 내는 거죠. 교수님 말로 "React의 엄청난 아이디어"예요. 대신 공짜는 아니에요. UI 상태를 메모리가 들고 있으니 메모리를 더 써요. React로 만든 페이지를 띄우면 크롬이 메모리를 꽤 먹는 이유예요.

틀린 생각State가 바뀌면 실제 DOM 전체를 새로 만든다
맞는 생각새 Virtual DOM과 이전 것을 비교해 필요한 실제 DOM만 바꾼다
시험엔 이렇게

Virtual DOM은 실제 DOM을 매번 직접 바꾸는 대신 UI 구조를 JS 객체로 메모리에 관리하는 방식으로, State 변경 시 새 결과를 계산해 이전 결과와 비교한 뒤 필요한 실제 DOM 변경만 수행한다. 깜빡임이 줄고 빨라지지만 메모리를 더 사용한다.

외우는 법: 복사본 · 새로 계산 · 비교 · 바뀐 곳만
바로 확인

빈칸 채우기 눌러서 정답 확인

React는 UI를 작은 Component로 나눈다. 부모가 자식에게 전달하는 데이터는 Props, 컴포넌트 내부의 변경 가능한 데이터는 State다. const [count, setCount] = useState(0)에서 상태를 바꾸려면 setCount를 호출하고, 그러면 리렌더링이 일어난다. React는 메모리의 Virtual DOM을 비교해 바뀐 부분만 반영한다. JSX는 빌드 시 React.createElement 코드로 변환된다.

    Q3Virtual DOM이 성능을 높이는 방식은?

    메모리에 UI 사본을 두고 비교해 필요한 곳만 바꿔요. 대신 메모리를 더 써요.

    Q4다음 중 선언형(Declarative) UI 코드는?

    상태(active, title)에 따라 UI가 무엇인지 선언. 나머지는 DOM 직접 조작(명령형).

    Q5JSX에 대한 설명으로 옳지 않은 것은?

    JSX는 HTML 자체가 아니에요. JS로 변환된 뒤 실행돼요.

    Q6State 변경 후 일어나는 순서로 옳은 것은?

    개발자는 State만 바꾸고, UI 계산과 DOM 업데이트는 React가 해요.

    Q7버튼(초깃값 0)을 2번 클릭한 뒤 <button onClick={() => setCount(count + 1)}>{count}</button>의 화면은?

    클릭마다 State +1 → 리렌더링 → 0 → 1 → 2.

    내 말로 설명하기 면접 대비

    "Virtual DOM의 구조와, 그걸로 리렌더링이 어떻게 일어나는지 설명해 보세요."

    실제 DOM은 브라우저가 가진 하나의 객체라, 바뀔 때마다 전체를 다시 그리면 느리고 화면이 깜빡여요(flickering). React는 UI를 JS 객체 형태로 메모리에 복사해 둔 Virtual DOM을 들고 있어요. 사용자가 버튼을 눌러 setState가 호출되면 State가 바뀌고, React는 새 Virtual DOM을 계산해서 이전 Virtual DOM과 비교해요. 그리고 달라진 부분만 실제 DOM에 반영해요. 그래서 조금만 교체해도 전체 페이지가 바뀐 효과를 내고 리렌더링이 빨라져요. 대신 UI 상태를 메모리에 들고 있어서 메모리를 더 사용해요.
